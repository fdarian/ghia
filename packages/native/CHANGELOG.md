# @ghia/native

## 0.14.0

`contenteditable` and the DOM editing model are in, so Lexical runs unchanged: editing hosts, live ranges, `Selection`, `beforeinput`, clipboard and paste events, and an Edit menu. Scrolling and text are faster (scroll pixel reuse, a per-glyph advance cache), a scroll no longer freezes when frames outlast a vsync, and stylesheets gain structural, form-state and `:has()` selectors. `<code code=... language=...>` is renamed `<code-block>`.

### Breaking changes

- **`<code code=... language=...>` is now `<code-block ...>`, and `<code>` is HTML's inline element.** The syntax-highlighted block keeps its props (`code`, `language`, `path`, `showLineNumbers`, `theme`) under the new name, so rename the tag (`<code-block code={source} language="ts" />`), the JSX type `CodeProps` to `CodeBlockProps`, and `findByType("code")` to `findByType("code-block")`. A `<code>` now lays out as `<span>` with the user agent style of Chrome's `code`: the generic `monospace` family, drawn at 13px beside 16px text by Chrome's monospace size rule (see `docs/reference.md`, "Monospace size"), so code that renders text inline in a paragraph (Lexical's Code format) works unchanged.
- **`pre`, `kbd` and `samp` use the generic `monospace` at Chrome's size**, not `Menlo` at the inherited size: they are 13px where the text around them is 16px, unless an absolute `font-size` is inherited or the `font-family` is a longer list (`monospace, monospace`). `tt` is a tag too.
- **`writeClipboardText` and `readClipboardText` on the renderer are `writeClipboard(items)` and `readClipboard()`.** Renderer code that called the old pair moves to the new one, which carries several types (see Clipboard below); `navigator.clipboard.writeText` and `readText` run on top of it.
- **A scroll no longer moves the hover under a pointer that stays, as in Chrome.** `:hover`, `style.hover` and `pointerover`/`pointerenter`/`mouseover`/`mouseenter` (and their out and leave twins) stay on the element the pointer last moved onto while a wheel runs, and follow to what is under it 500 ms after the last tick of a mouse wheel, 100 ms after a trackpad lift (momentum that follows runs the 500 ms again), at the next frame after code scrolls an element by any path (`scrollTop = n`, `scrollTo`, `scrollIntoView`, `scrollToItem`, a key, a scrollbar; a smooth scroll when it ends), or at the next frame after a frame that changed the page (a commit, a restyle, a resize) or ran an animation of the layout (a transition or animation of a size, a margin, a position or the like, or a `layout` glide; a color, an opacity or a transform does not count, so `transition-colors` on rows and a spinner leave the hover where the wheel put it). A pointer that moves follows at once. `getPatchCounters().scrollPatch` loses `hoverAsked` and `hoverMatters` and its `held` loses `HitboxChain`; `Hover` holds a frame for a pointer that moved only. A test that wheels and expects the row under the pointer to be hovered calls `advanceTime(500)` and draws the frames the follow asks for.

### Features

**Editing and contenteditable**

- `contentEditable` is the DOM's: it reflects the `contenteditable` attribute, `isContentEditable` reads it with inheritance, an editing host is focusable (`focus()`, Tab, `tabIndex` 0), and `:read-write` / `:read-only` count editable elements. Nothing edits yet.
- Typing into an editing host (`<div contentEditable>`): what the keyboard types, a dead key's result, the emoji picker and dictation reach the focused host through the window's input handler, once, as `beforeinput` (an `InputEvent` that bubbles and can be canceled: `insertText`, or `insertReplacementText` for a range the platform replaces), the change to the DOM, then `input`. An unprevented Enter, Backspace or Delete `keydown` does the same, keeps the platform from typing the key as well, and an editing host always gets its `keydown`, with no listener on its path. The edit goes through `insertData` and `deleteContents` so a `MutationObserver` sees it and the selection follows. `InputEvent` has `targetRanges` and `getTargetRanges()`. The test renderer has `simulateEditingInput` and `simulateEditingComposition`.
- An input method composes in a focused `contenteditable`: marked text, a dead key (Option+E, then E) and a commit fire `compositionstart`, `beforeinput` (`insertCompositionText`), `compositionupdate`, `input` and `compositionend` in Chrome's order, and the platform is told where the marked text is (the candidate window) and which character a point is on. The composition ends with `compositionend` when the host loses focus. `simulateComposition` now composes in an editing host through the same text input, and the test renderer has `getInputMethodBounds` and `getInputMethodIndexAtPoint`.
- A focused `contenteditable` host moves the caret and deletes by word and line from the keyboard, as Chrome on macOS does: Left and Right by character (a range collapses to its edge), Option by word, Cmd to the row boundary; Up and Down by painted row keeping the column, Cmd to the start or end of the host; Shift extends each, and Shift+Home and Shift+End extend to the host's edges. Cmd+A selects the host's contents, the Emacs moves Ctrl+B, F, N, P extend with Shift, Ctrl+H and Ctrl+D delete, and Option+Backspace, Option+Delete and Cmd+Backspace fire `beforeinput` with `deleteWordBackward`, `deleteWordForward` and `deleteSoftLineBackward` and `targetRanges` before they change the DOM. Each is a `keydown` default, so `preventDefault()` stops it. Bindings Ghia does not do are listed in `docs/fork/deviations.md`. Home, End, Page Up and Page Down scroll the nearest scroller while a host has focus (the arrow keys and Space stay editing keys and do not scroll, and Shift+Page Up and Down scroll nothing).
- A click in a `contenteditable` host puts the caret at the character under the pointer and focuses the host with the selection already there, Shift+click extends the focus, and a drag selects from the press to the pointer, clamped to the host. A double click selects the word, a triple click the contents of the paragraph, and a drag after either extends by words or paragraphs. The selection is a node selection, so it is painted as the caret or the wash, `selectionchange` fires and a framework editor (Lexical) reads it; a prevented `mousedown` changes nothing, and a press outside every editing host still selects painted text. No auto-scroll at the edge while dragging in a host and no `selectstart` yet: see `docs/fork/deviations.md`. A press, a drag or a double or triple click on an empty paragraph (`<p><br></p>`) puts the caret in it, as `(paragraph, 0)`.
- Editing hosts follow the DOM at the edges: moving an editable subtree into or out of an editing host updates what takes focus (an editable element inside an editable parent is not a tab stop), and Tab or `focus()` into a host puts the caret at its start (a click focuses first, then puts it at the point). Setting the selection inside a host that does not hold focus (`setBaseAndExtent`, `collapse`, `addRange`, ...) focuses the host, as Chrome does, so Lexical's `editor.focus()` moves focus into an editor. A host matches `:focus-visible` after a click, as in Chrome, and a focused `contenteditable` host dims no other focusable element, as a text field does not.
- The caret of an editing host is painted: a collapsed selection inside a focused `contenteditable` in a key window draws a 2px caret a row high in the theme's caret colour, solid when it moves or comes and blinking every 500 ms like an `<input>`'s. A blink is a patched frame that builds only the paragraph that holds the caret, and a host that has no focus or a window that is not key asks for no frame. `getPaintedNodeSelection()` in the test renderer now returns `{ washes, caret }`.
- A node selection inside an editing host is painted: the text between its two points gets a selection wash in every paragraph it reaches, in the colour of a dragged selection. Changing the selection builds only the paragraphs it touches (retention skips the rest). The selection goes to native in the mutation batch (`setNodeSelection`, wire opcode 16).

**Ranges, selection and the DOM from code**

- `Range`, `StaticRange` and `AbstractRange` exist, with `document.createRange()`. A `Range` is live: a tree change, including a React or Solid insert, removal or text update, and a data change move its boundary points as the DOM standard says. `CharacterData` has `substringData`, `appendData`, `insertData`, `deleteData` and `replaceData`, `Text` has `splitText` and `wholeText`, and `document.hasFocus()` answers.
- `getSelection()` holds a live `Range` of nodes once code selects them: `anchorNode`, `focusNode`, `direction`, `getRangeAt`, `addRange`, `removeRange`, `collapse`, `extend`, `setBaseAndExtent`, `selectAllChildren`, `containsNode`, `deleteFromDocument`, `getComposedRanges` and `modify` by character and word, with the DOMExceptions of the standard. A node selection and the painted text a drag selects replace each other. `document` hears one coalesced `selectionchange` per burst of changes, including a move caused by a tree or data change.
- `Range.getClientRects()` and `getBoundingClientRect()` are the rects of the selected text, one for each painted line of each Text node and the border box of each element the range selects whole, and a collapsed range in text is the caret rect. `document.caretPositionFromPoint(x, y)` (with the `CaretPosition` global) and `document.caretRangeFromPoint(x, y)` give the text position nearest a point. `Selection.modify` takes the `line`, `lineboundary` and `documentboundary` granularities: moves by line keep the caret's x across a short line. Native has three new reads for them (`getTextRangeRects`, `caretPositionFromPoint`, `moveCaretVisually`).
- `document.createDocumentFragment()` makes a real `DocumentFragment`: it holds children, is never mounted, and inserting it (`appendChild`, `insertBefore`, `replaceChild`, `append`, `before`, `Range.insertNode`, ...) moves its children in order. `Range.cloneContents()`, `extractContents()` and `surroundContents()` are there.
- `DOMParser` parses `text/html` into an inert `Document` (real `Element`, `Text`, `Comment` and `DocumentFragment` nodes with `style`, `querySelector`, `<template>` content and a `styleSheets` list of `CSSStyleSheet`s built from its `<style>` elements; `CSSStyleRule.style` reads a rule's declarations), and `innerHTML`, `outerHTML` and `insertAdjacentHTML` read and write markup on an element, in its context, so the new children are drawn. HTML is parsed and serialized by parse5 through a tree adapter over Ghia's own nodes. `Comment`, `StyleSheetList` and `Element.namespaceURI` are there; `textContent` skips comments. The XML MIME types and `XMLSerializer` are not supported: `docs/fork/deviations.md`.

**Clipboard**

- `DataTransfer`, `DataTransferItemList`, `DataTransferItem` and `ClipboardEvent` are globals. `new DataTransfer()` is an empty read/write store with `items`, `types`, `files`, format normalisation and the DOM's read-only and protected modes, and the `dataTransfer` of a drag is an instance of it. `copy`, `cut` and `paste` are `ClipboardEvent` types with `onCopy`, `onCut` and `onPaste` props in React and Solid.
- Cmd+C, Cmd+X, Cmd+V and Cmd+A, and a new Edit menu (Cut, Copy, Paste, Select All), run as one set of GPUI actions. Outside an `<input>` or `<textarea>` they fire the DOM `copy`, `cut` and `paste` events at the element that holds the start of the selection (the focused element with no selection), with a `DataTransfer` in the mode the Clipboard API gives it; a cancelled `copy` or `cut` writes exactly what the handler put in `clipboardData`, and an uncancelled `copy` writes `text/plain` (line breaks between blocks and at a `<br>`, as Chrome copies it) and `text/html` of the node selection (a text selected by dragging is still copied as before). A checkbox, radio, range or hidden `<input>` is not a text control: it gets the events. A `preventDefault` on the `keydown` cancels the command. Select All selects the focused editing host, or the body. In an editing host, an uncancelled Cut copies the selected range and deletes it (`beforeinput` `deleteByCut`, then `input`), and an uncancelled Paste inserts the clipboard's text (`beforeinput` `insertFromPaste` with `dataTransfer` and `targetRanges`, a `<br>` for each line break, `input`); a caret, or a selection outside a host, does nothing, and so does a clipboard with no text after the `paste` event. `Element.innerText` is new. `document.execCommand('copy' | 'cut' | 'selectAll')` run the same commands synchronously (an `execCommand` cut fires no `beforeinput`, and a call made from the event of another returns false), `'paste'` and every other command return false, and `queryCommandSupported` and `queryCommandEnabled` answer for them. `TestRenderer.simulateMenuAction(name)` chooses an Edit menu item. `<input>` and `<textarea>` fire no clipboard events: `docs/fork/deviations.md`.
- The clipboard carries several types. `writeClipboard(items)` and `readClipboard()` on the renderer replace `writeClipboardText` and `readClipboardText`: `text/plain`, `text/html` and `text/uri-list` use their pasteboard types, and every other type, such as `application/x-lexical-editor`, goes into Chrome's `org.chromium.web-custom-data` entry, so a page here and a page in Chrome exchange them. `navigator.clipboard.writeText` and `readText` run on top, and the test renderer holds the entries in memory.

**Stylesheets**

- Stylesheets support the structural pseudo-classes: `:first-child`, `:last-child`, `:only-child`, `:nth-child(An+B)`, `:nth-last-child(An+B)`, `:first-of-type`, `:last-of-type`, `:only-of-type`, `:nth-of-type(An+B)`, `:nth-last-of-type(An+B)` and `:empty`, in any compound and inside `:is()`, `:where()` and `:not()`. Before, a rule that used one was dropped. A child that comes, goes or moves restyles only the siblings whose position it changes (the two neighbours for `:first-child` and `:last-child`, the siblings after it for `:nth-child()`, before it for `:nth-last-child()`, the parent for `:empty`), and a sheet that uses none of them marks nothing extra. `:nth-child(An+B of S)` is still not supported.
- Stylesheets support the form and tree state pseudo-classes `:disabled`, `:enabled`, `:checked`, `:indeterminate`, `:required`, `:optional`, `:read-only`, `:read-write`, `:any-link` and `:link`, in any compound and inside `:is()`, `:where()` and `:not()`. Before, a rule that used one was dropped. A prop or a click that changes one of them restyles only the elements that read it (toggling `disabled` on one of a thousand buttons matches that button again; checking a radio matches it and the radio it unchecked), and a sheet that uses none marks nothing extra. `:placeholder-shown`, `:invalid`, `:valid`, `:default`, `:open`, `:autofill` and the range pseudo-classes are still not supported.
- Stylesheets support `:has()`: `:has(> img)`, `:has(+ p)`, `:has(~ .x)` and `:has(.err)` (a relative selector list, with `>`, `+`, `~` or a descendant as the leading combinator), in any compound and inside `:is()`, `:where()` and `:not()`, so `.card:has(.err) .title`, `.btn:has(> svg)`, `h1:has(+ p)` and `.field:has(input:checked) .label` style what they name. Before, a rule that used it was dropped. A class, id, attribute, tree state or position an argument reads, and a child that comes, goes or moves, restyle only the elements that hold what the `:has()` compound requires and that are above or before the one that changed, and a sheet with no `:has()` marks nothing extra. `:has()` is not forgiving, does not nest, and takes no pointer or focus state (`:has(:hover)` is invalid; `hasHover` is the style key for that).

**HTML tags**

- List markers. `li` is `display: list-item` and has a marker: a bullet (`disc`, `circle`, `square`, drawn as shapes sized by the font's ascent as Chrome draws them) or a number (`decimal`, `lower-alpha`, `upper-alpha`, `lower-roman`, `upper-roman`, with Chrome's counter text `1. `). `list-style-type`, `list-style-position` and the `list-style` shorthand are inherited properties; an `outside` marker ends at the item's border box on its first line and takes no part in layout, an `inside` one takes room at the start of the first line. The number is the item's place among the list items of its parent, from `start`, down with `reversed`, and set by an item's `value`; `ol start`, `ol reversed` and `li value` reach native from React and Solid (`forwardsCustomProp`), and the DOM properties `li.value`, `ol.start` and `ol.reversed` reflect them as in the DOM (Lexical assigns `li.value`). Inserting, removing or moving an item, or changing one of those or the type, renumbers the items after it in a retained frame. A `ul`, `ol` or `dl` inside a list has no block margin and a `ul` is a `circle` inside one list and a `square` inside two, as in Chrome. An `outside` marker is the item's for the pointer (`elementFromPoint`, clicks, `:hover`), an `inside` one follows `text-align` and re-measures its text when the number gets wider, the counter's digits are tabular as in Chrome's `::marker`, and `list-style` works in `:hover` and `hover` styles. Painted against headless Chrome's ink at scale 1 and 2 (`list-markers` oracle, React and Solid), and Lexical's list commands now show their bullets and numbers. Not supported: `::marker` styling, `list-style-image`, `counter-*`, `@counter-style`; the counter's scope is the parent element (`docs/fork/deviations.md`).

**Text and fonts**

- `font-family` is a list, as in CSS: the first installed family draws, the installed ones after it are the fallbacks for the glyphs it lacks, and `system-ui`, `-apple-system`, `BlinkMacSystemFont`, `sans-serif`, `serif`, `monospace`, `cursive`, `fantasy` and `math` map to what Chrome uses on macOS. A web font stack no longer falls through to GPUI's fallback face. `<code>` takes the list too.
- Chrome's monospace font-size rule: an element whose `font-family` becomes the generic `monospace` alone has its `font-size` scaled by 13/16 when that size is not an absolute length, and scaled back where the family stops being `monospace`.

**SVG**

- An `<svg>` child takes the kebab-case attribute names the DOM and Solid write (`stroke-width`, `stroke-linecap`, `fill-rule`) as well as React's camelCase props, and a transition or `@keyframes` on one reads the kebab-case attribute as it reads React's prop.

### Performance

- A scroll of a list copies the pixels that stay and draws only what scrolled in, instead of drawing the whole list again: a wheel translate presents the list's pixels moved by the scroll plus the strip of rows that came in and the scrollbar's thumb, and each part of the frame draws only the primitives that meet it (a translate frame of a mailbox-shaped scene: 0.38 ms of GPU time to 0.24; the scroll phase of the live mailbox -27%). The picture is the same as a whole draw. `getPatchCounters().scrollPatch` gains `shifted`, the presentations whose damage carried a shift, and `GPUI_GPU_TIMES` lines gain `shift=<dx>,<dy>|none rects=<n>`.
- Scrolling builds fewer rows that hold a `position: relative` or `absolute` box. A row that hands such a box to the stacking context around it was built again on every scroll frame; its recording now carries the box (its paint and its hitboxes are recorded with the row and put where the scroll moves it), so the row is moved. A row whose box is cut differently where the scroll puts it (a rounded clip inside the box) is built.
- Scrolling inside a rounded `overflow: hidden` panel or card builds fewer rows. A retained row under a rounded content mask used to be built again on every scroll frame; it is now moved when it stays clear of the mask's rounded corners, and only the rows that reach a corner are built. Where a row is clear of the corners the pixels are near those of painting under the rounded mask (paths cut by an unsnapped mask may differ), and a row that reaches a corner is built.
- A scroller that is no virtual list (TanStack Virtual's div scroller) records its rows for the travel of a row that is shown, three viewports of the scroller, as a list does, so a row is no longer built again while it is shown after a few 30 px wheel steps.
- A wheel under a still pointer is a translate whatever hover the rows have (407 of 720 ticks were translates in the mailbox proxy with a live hover, 668 are). Before, every wheel tick followed the hover, and the tick that did met the next wheel, so about every other frame of a live scroll over a `<virtual-list>` was built whole. A row that comes in under a still pointer is a translate too; it was declined as `Pointer` (`applyDeclines.Pointer` is gone), because a scroll no longer moves the hover under a pointer that stays.
- A wheel event over a `<virtual-list>` whose draw meets the hover tick of the previous wheel is a patch and a translate in one draw. The wheel notifies the list's view, and a patch declined a draw with a view queued (`PendingView`), so the tick's hover patch was refused and the gate then saw its hover paint as an edit. A patch now goes through when the only queued view is the one the scrolled list named, and the translate follows it in the same draw; any other queued view still declines. The test renderer takes `setHoverResyncByFrame(false)` to resync the hover from the draw that moved the rows, as a window does.
- A hover that follows a scroll is a patch when the row it leaves is one the scroll took out of the frame. The hover follows late (when the scroll ends or a build changed the page), so the previous hover is usually a row of a `<virtual-list>` that the frame shown no longer holds; the patch declined it as `Hover`.
- A row of a `<virtual-list>` that a frame built whole replayed at a moved place is patched too (it was `Hover:Relocated` until something built the row again), and so is a row that holds an `overflow: hidden` box, such as an ellipsized line of text. A box only code scrolls (`scrollTop`) has an offset and an extent relative to its padding box, which moves with the row, and the bounds its scroll handle reports move with the recording. Only a row with a box the user scrolls, or one that has a non-zero offset, still declines.
- A hover that crosses the rows of a TanStack Virtual list (`position: absolute` with a `transform`, a `:hover` background and an absolutely positioned box of their own) is a patched frame, as it was for the rows of `<virtual-list>`: 3.2M instructions a crossing, not 8.9M. A root that lifts itself and forms its own stacking context is a hover patch root; one that something lifts out of, into the context around it, still is not.
- The frame of a key, click or other input that reaches an idle window is drawn and presented by the frame loop right after the tick that dispatched it and the microtasks that tick's handlers queued (as a browser paints after an input task and its microtasks), where it waited for the display link's first vsync (7 to 10 ms at 120 Hz) before. The renderer has two new methods for it, `startedLinksPending()` and `stepStartedLinks()`; `tick()` itself draws nothing. `GPUIX_INPUT_FRAME_OFF=1` restores the wait.
- Mounting new text asks CoreText again only for glyphs no earlier text used (a cold Settings dialog mount frame: about 10% fewer instructions).
- Mounting a subtree asks the layout engine fewer questions: a node's layout input drops the parent size it does not read and a block container's available height it does not read, so equal questions share one cache entry (a Settings dialog mount sizes 2188 nodes instead of 3185, 8% fewer instructions).
- The HTML parser (parse5) loads on the first `DOMParser.parseFromString`, `innerHTML`, `outerHTML`, `insertAdjacentHTML` or HTML paste and not at startup, so a plain app starts with 0.4 MB less JS heap and, run from the bundle, 12 to 17 ms and about 2.5 MB less footprint. The web (wasm) build no longer bundles parse5.

### Fixes

- A scroll no longer freezes while frames take longer than a vsync. The macOS pump ran display-link frame steps back to back in one tick for as long as the link had another one queued, so wheel events were not read and JS did not run for 0.1 to 2 s at a time, and the page kept presenting a frozen scroll. A tick now runs at most one frame step, and the next tick reads the events first.
- Each key event from the keyboard gets its own microtask checkpoint on both sides: `tick()` ends its pump before a `keydown`, `keyup` or modifier change when an event or a frame step came first, and after sending it, and the frame loop ticks again at once, so an editor that commits its update in a microtask (Lexical) applies every key that was waiting, where it used to keep the first and lose the rest. With `frameMs` set the timer path ticks again on the next turn of the event loop (`keyEventPending()`) instead of waiting out the frame. There is still no checkpoint between the listeners of one event or between a key's `keydown` and its `input`, and mouse events handled in one pump share one. The test renderer gets `postNativeKeys`, `pumpNativeEvents`, `setYieldAfterKeyEvent` and `keyEventPending` to drive that pump.
- The live automation client presses a `keystrokes` sequence one key at a time with a turn of the event loop after each, so an editor that commits its update in a microtask (Lexical) takes every key of "m i d" and not only the first. A synchronous `simulateKeystrokes` on the test renderer still runs a sequence inside one call; the limit is in `docs/fork/deviations.md`.
- The text editor's events (`input`, `compositionstart`, `compositionupdate`, `compositionend` and the number stepper's `change`) reach JS synchronously on macOS, in the test renderer and in the web (wasm) renderer, as `keydown` does: after the edit and before the key's `keyup`, in order, in the same tick as the key. A controlled input's echo is drawn by the frame of the key that typed it, where it waited for the next tick before. They are still queued on Windows and Linux.
- A block whose only content is a line break (`<div><br></div>`, `<p><br></p>`, or a lone `"\n"` under `white-space: pre`) is one line tall, as in Chrome, and not zero. `a<br>` stays one line and `<br><br>` is two.
- `xlink:href` and `xlinkHref` on an SVG `<use>` are written as `href`, and the `marker` shorthand no longer writes a marker twice beside a longhand.
- `TestRenderer.dispose()` closes the window itself, while its app is alive, and no longer leaves that to a block on the main queue. A block still queued when the app was released ran in the next renderer's `dispose()` and aborted the process with "app was released before async operation completed". `RowOracle.dispose()`, and a `RowOracle` that a newer one replaces, close their window the same way.

  Two test-only methods: `TestRenderer.disposeLeavingMainQueueForTest()` (`dispose` without running the main queue, so the close block stays queued) and `runMainQueueToMarkerForTest()` (runs the main run loop until a block queued now on the main dispatch queue has run, so every block queued before it has; throws after 5 seconds).

## 0.13.0

The tree is now a DOM. Every window root is `<html>` with `<head>` and `<body>`, nodes are real `Node`, `Element` and `Text` objects, CSS stylesheets and HTML tags work, and code that is not the framework can build, query, style and observe the tree as it does in a browser. As a result these run unmodified: `@base-ui/react` (Checkbox, Switch, Radio, Slider, Field, Popover, Menu, Select), Kobalte and the Base UI Solid ports, the `@dnd-kit/dom` sortable (`@dnd-kit/solid` and `@dnd-kit/react` 0.5.3), floating-ui and TanStack Virtual.

### Breaking changes

- **`<text>` is only an SVG element now.** A string is a DOM text node and goes directly into any element (`<div>Saved</div>`, or strings and `<span>`s as one inline paragraph). `<text>` outside an `<svg>` throws `<text> is only valid inside <svg>`. To migrate, turn a `<text>` that sat inside other text or a `<span>` into a `<span>`, any other `<text>` into a `<div>`, or put the string straight into its parent. `findByType("text")` and tests that read a string node's type now use `"#text"`.
- **`id` is the DOM `id`.** On a host element, `id` is the `id` prop as a string (`""` without one). The number native knows an element by is now `nativeId`, on host elements and text nodes of both adapters. Migrate `renderer.scrollToItem(ref.id, i)` to `renderer.scrollToItem(ref.nativeId, i)`; `FocusableNode` and `ObservableElement` take `nativeId` as well.
- **A text control's `change` fires on commit (Solid and native).** `onChange` and `addEventListener('change')` on an `<input>` or `<textarea>` fire when the user commits a changed value (blur, or Enter in an `<input>`), as in the DOM, instead of on every edit. Move per-keystroke handlers to `onInput` (`HostInputEvent`); `onChange` now receives a `HostChangeEvent`, a plain `Event` rather than an `InputEvent`. Solid's `ComboboxInput` reports through `onInput`. React apps need no change: `onChange` still fires per edit as React DOM's does, and `addEventListener('change')` on a ref gives the commit. For renderer code, `getTextSelection` no longer carries the text; read it with `getTextValue`.
- **Top-level nodes live in `<body>`.** A window root is `<html>` > `<head>` + `<body>`, and the app's top-level nodes are children of `body`, so several top-level siblings all draw (only the last one did). Event paths end at `html`. `<html>` and `<body>` are `display: block`, fill the window and have no default margin.
- **`document.activeElement` is `document.body` when nothing is focused**, where it was `null`, and a key pressed with nothing focused targets `body` and bubbles through `html`, `document` and `window`, where it went to `window` alone with `target === null`. Replace `document.activeElement === null` with `=== document.body`, and a `window` key listener's `event.target === null` check with `=== document.body`.
- **`querySelectorAll` returns a static `NodeList`**, not an `Array` subclass, so it has no `map` or `filter`, as in a browser. Wrap it in `Array.from(...)`. `children` and `childNodes` stay arrays.
- **Host node fields renamed.** A Solid host node's child list is `childList`, because `children` is now the DOM's elements-only list, and a host node's `tag` field is `elementType`.
- **Host element types follow React DOM and solid-js**, which can fail a build that passed: React's `JSX.IntrinsicElements[tag]` props carry the tag's DOM `ref` (`useRef<HTMLDivElement>` on a `div`), which Ghia's own components (still `Ref<PublicInstance>`) do not accept; a callback ref typed narrower than the tag's instance no longer fits; under `moduleResolution: "nodenext"` JSX props are now type-checked where they were `any`; and in Solid a `<li>` callback ref's `value` is `never`.
- **Text selection only on text-like inputs.** `selectionStart`, `selectionEnd` and `selectionDirection` are `null`, and `setSelectionRange()` throws `InvalidStateError`, on every `<input>` type except `text`, `search`, `url`, `tel` and `password`, as HTML says. `email`, `number` and `date` used to have a selection; `select()` still selects their text.
- **For custom adapters and renderer code.** `className` is no longer a native element prop; it is the `class` attribute, sent with the other attributes. Adapters implement the new `ParentBinding`, `TextBinding` and `ElementBinding` members on their `DOM_BINDING`, register a `DomNodeFactory` with `installElementSource`, and join `unmountAllRoots()` through `registerRoot()`. `appliedBatchCount` moved from `@ghia/native/host` to `@ghia/native/testing`.

### Features

**Stylesheets**

- `<style>` elements and constructed sheets (`new CSSStyleSheet()` in `document.adoptedStyleSheets`, with `replace`, `insertRule`, `deleteRule` and `cssRules`) style the tree. Type, class, id and attribute selectors, `:is()`, `:where()`, `:not()`, `:root`, the four combinators, nesting and `@layer` match, and `!important` is honoured against the `style` prop. `@media`, `@keyframes`, pseudo-elements and the other at-rules are skipped; see `docs/fork/deviations.md`.
- Stylesheets read `:hover`, `:active`, `:focus`, `:focus-visible`, `:focus-within` and `:popover-open`, and a new inline `focus` style block applies while the element has focus. Focus styles transition and pass inherited values (`color`, `fontSize`) to children.
- `initial`, `unset`, `inherit` and `revert` take back user agent and base styles as in CSS, in sheets, inline styles and state blocks.
- `var()` works in every style property (`width: "var(--anchor-width)"`, colours, borders), with fallbacks, and transitions run between computed `var()` values.

**HTML tags and form controls**

- HTML tags are host elements with Chrome's default style and implicit accessibility roles: `<p>`, `<h1>` to `<h6>`, lists, `<section>`, `<nav>`, `<main>`, `<table>` and its parts, `<strong>`, `<em>`, `<a>`, `<br>`, `<button>` and the rest listed in `docs/reference.md`. Inline tags join their parent's paragraph like a `<span>`. `<button>` and `<a href>` are tab stops, Enter and Space click a focused button, and a button submits its form (`event.submitter`, `form.requestSubmit(submitter)`).
- `<input type="checkbox">`, `"radio"`, `"hidden"` and `"range"` work as in HTML: toggling and radio groups, `input` then `change`, `checked`, `defaultChecked`, `indeterminate`, `valueAsNumber`, `stepUp()`, keyboard stepping for a range, and `FormData`. They paint nothing themselves, since Base UI draws its own; see the deviations.
- Text controls fire `input` (an `InputEvent` with `inputType` and `data`) once per edit and `change` on commit, at the DOM's times.
- The constraint validation API on `<input>` and `<textarea>`: `required`, `validity` (`valueMissing`, `customError`), `setCustomValidity()`, `checkValidity()` and `reportValidity()`. `ValidityState` is a global.
- `setAttribute('value' | 'checked')`, `defaultValue` and `defaultChecked` behave as the DOM's defaults, and `value`, `checked` and `indeterminate` can be written before the element mounts.

**The DOM from code**

- `Node`, `Element`, `HTMLElement`, `SVGElement`, `Text`, `Document` and the `HTML*Element` classes Base UI checks are real classes, exported by `@ghia/native/host` and installed as globals where the runtime has none.
- Build and move nodes from code beside the framework's: `document.createElement`, `createElementNS`, `createTextNode`, `appendChild`, `insertBefore`, `removeChild`, `replaceChild`, `remove`, `before`, `after`, `append`, `prepend`, `replaceChildren`, `cloneNode` and the `textContent` setters. React and Solid pick up the tree the code left.
- `matches`, `closest`, `querySelector` and `querySelectorAll` take real CSS selectors, compiled once and cached. `getElementsByTagName`, `getElementsByClassName`, `getElementsByName`, `getElementById` and `document.createTreeWalker` are there too.
- `MutationObserver` with the standard's options and delivery. With no observer alive it costs one integer check per change.
- `setAttribute`, `removeAttribute` and `toggleAttribute` write the prop through the framework's own path, so `aria-hidden`, `inert` and `data-*` set by floating-ui or Base UI reach native at once. `classList` and a live `dataset` come with them.
- `element.style` is a `CSSStyleDeclaration` over the live style (`setProperty` with `important`, `getPropertyPriority`, `cssText`, camelCase members), merged with the framework's own style updates.
- Layout reads: `getComputedStyle`, `offsetWidth`/`offsetHeight`, `offsetParent`/`offsetLeft`/`offsetTop`, `clientLeft`/`clientTop`, `getClientRects()`, `document.elementFromPoint` and `elementsFromPoint`.
- Events: delivered events are instances of `PointerEvent`, `MouseEvent`, `KeyboardEvent`, `FocusEvent`, `InputEvent` and the other DOM classes (with `getModifierState`), `element.dispatchEvent` and `document.dispatchEvent` run capture, target and bubble (and a dispatched `click` activates labels and submit buttons), and `addEventListener` takes `capture`, `once`, `passive` and `signal`. `onKeyDownCapture`, `onKeyUpCapture`, `onFocusCapture` and `onBlurCapture` (plus `onFocusInCapture` and `onFocusOutCapture` in Solid) used to be dropped silently.
- The popover API: `popover`, `showPopover()`, `hidePopover()`, `togglePopover()`, `beforetoggle` and `toggle`, drawn in the top layer with light dismiss for `popover="auto"`.
- Web Animations: `element.animate(keyframes, options)` returns the same `Animation` that `getAnimations()` lists, and `KeyframeEffect`, `Animation`, `CSSAnimation`, `CSSTransition` and `DocumentTimeline` are globals.
- `window` has `innerWidth`, `innerHeight`, `visualViewport` and a `resize` event; `requestAnimationFrame` runs in the window's frame steps; `ResizeObserver`, `IntersectionObserver` (which takes `document` as its root) and `matchMedia` are globals; `document.getSelection()` and `selectionchange` exist.

**Solid**

- JSX written with HTML attribute names works: `autofocus`, `tabindex`, `readonly`, `maxlength`, `colspan`, `rowspan` and `for`.
- `style` takes CSS-named keys (`'white-space'`, `'z-index'`, `-webkit-app-region`) and a CSS text string (`style="color: red"`), as Solid on the web does. A style typed as solid-js's `JSX.CSSProperties` is assignable without a cast.
- Host props accept what solid-js types for the same attribute, so `JSX.HTMLAttributes` spreads onto a host element.

**React**

- Host elements take `className` and `<style>` is a JSX element. Refs are typed by the tag's DOM interface, so TanStack Virtual's `measureElement` needs no cast; `HostRef`, `TextControlInstance` and `FormInstance` are exported.
- Suspense and Activity hide a child through its live `style` as React DOM does.

### Performance

- Plain fills are drawn by a lighter fragment shader. In the Mailbox bench the GPU time of the scroll phase fell from about 540 to 370 ms, typing from 40 to 26 ms and navigating from 40 to 28 ms, close to GPUI alone (341, 25 and 29 ms).
- A layout edit is patched at the fixed-size box that holds it instead of laying out the whole frame: a text edit in a row of a 10,000-row list went from 323M to 1.7M instructions, about the cost of a hover. `GPUIX_BOX_ROOTS_OFF=1` turns it off.
- Absolutely positioned rows, the shape TanStack Virtual renders, are kept and moved between frames instead of rebuilt, and inserting a row no longer rebuilds the rows after it.
- A wheel on a scroller is a scroll write, so a scroll listener that reads `scrollTop` no longer forces a layout pass per wheel event. A caret blink is no longer a whole frame after a stylesheet sets `white-space`.
- A stylesheet change reparses only new rules and rematches only the elements a changed rule can reach (`insertRule` at 10,000 elements: 21M to 1.1M instructions), and a class toggled on 5,000 elements costs about half what it did.
- A layout read (`scrollTop`, `clientHeight`, `scrollHeight`) after swapping out class-styled content, such as a Solid `<Show>` swap, patches the frame instead of building it whole. An element outside the document no longer counts as a change of the frame.
- An element with no `var()` skips substitution, about 1% fewer instructions when scrolling a long list.

### Fixes

- A style value that does not parse (`border: 0`, `height: "inherit"`) drops only that declaration, as in CSS, instead of rejecting the style and unmounting the app.
- `onScroll` runs before the frame that paints the new offset, so a virtualizer shows the right rows with no blank frame.
- A transition or animation below an element that goes `display: none` is cancelled, as in a browser.
- `element.animate()` keeps running after the element is removed, and `getKeyframes()` of a retargeted transition no longer throws.
- A throw while flushing no longer stops later flushes. Solid's `render()`, `flush()`, `flushSync()`, `dispatch()` and `unmount()` and React's `unmount()` finish their work and then rethrow (one error, or an `AggregateError`), a Solid root without `onUncaughtError` logs errors with `console.error`, and a throwing `onCleanup` no longer leaves a Solid root unable to render.
- A prop that leaves a Solid spread is removed, and children that change through a spread replace the old nodes instead of being appended.
- `element.focus()` does nothing on an element that is not rendered (`display: none`, `visibility: hidden`, `inert`), as in a browser.
- An element used after its window closed, or after a test renderer was disposed, behaves as a detached node instead of throwing or reaching another window. Handlers that moved focus to each other in a loop throw `Maximum call stack size exceeded` instead of aborting the process.
- `document.documentElement`, `head` and `body` are never `null`; what code writes to them before the first `render()` carries over to the real root.
- A full reload under `ghia dev` unmounts the roots before running the entry again, as a page reload does.
- `<label for>` names its control in React, and in Solid on every element.
- `draggable` reflects as `"true"` or `"false"`, as the DOM does.
- `selectionStart` and friends on a checkbox, radio, range or hidden input are `null` instead of throwing.
- A required radio outside the document reports `valueMissing` correctly.

## 0.12.1

Mostly performance: the mutation batch is one binary byte array, and commits, hovers and list scrolls are drawn by patching or moving what is on screen where the page was built whole.

### Breaking changes

- **`applyBatch` takes the bytes of the mutation batch, not a JSON string.** This breaks anything that calls `applyBatch` itself on the live, test or wasm renderer; tests that built or parsed a batch use `encodeWireBatchForTest` and `decodeWireBatchForTest` from `@ghia/native/testing`. `MutationRenderer.setStyle` takes the style's JSON text as an optional third argument, which Solid passes from the text its write comparison already made, so a written style is stringified once.

### Performance

**Mutation batch**

- The mutation batch is one binary byte array instead of JSON text. `createMutationQueue` writes each op as it is enqueued through `WireWriter` (internal to `@ghia/native`, `js/wire.ts`; not exported) into reused buffers, with no tuple per op and no `JSON.stringify` of the batch, and `applyBatch(bytes: Uint8Array)` on the live, test and wasm renderers decodes it in place (`batch::wire`), so the napi call transcodes no string and the decoder allocates nothing per op beyond what it keeps. The format is specified in `docs/reference.md` ("Wire format"). A failed batch is put back in front of what was enqueued since, and a style native rejects is cut out of the batch by its byte range, as before.
- `createMutationQueue` walks a style for `blob:` URLs only when the style's JSON text contains `blob:`, instead of walking every style it sends.

**Patch frames**

- A commit that only changes how elements paint is drawn as a patch frame, as a hover that only paints is: the roots that hold the restyled elements are built again and gpui writes the primitives they paint over the frame shown, and the layout stays current, so a read of `scrollTop` or `clientHeight` after the commit runs no layout pass. A restyle qualifies when it keeps the operations of the root (the comparison a hover makes: colours that keep their visibility, an opacity on the same side of 1, a background quad that is kept in both styles). A state style (`hover`, `hasHover`, `focusVisible`, ...) whose refinement differs only in paint is a paint change now; it made the style a layout change, so the mailbox row of ghia-bench took a layout pass for a selection. Anything else, or an element no root of the last frame built whole holds (`getPatchCounters().unpatchable.Commit`), is drawn whole as before.
- A commit whose layout and structure changes all lie inside a scroller (an overflow `auto` or `scroll` element that holds nothing else the retention excludes) is drawn as a patch of that scroller, whatever it holds (text, boxes with children, a keyed swap of the content with another number of elements), where it was a frame built whole: the scroller is built and laid out again, gpui splices its ranges into the frame, and the patch is accepted when nothing outside it moved (`getPatchCounters().relayoutPatches`, `rewrittenRecordings`). A change outside every scroller is counted as `unpatchable.Structure`, a patch whose box would leak out as `declines.NotContained`. A read of boxes or scroll metrics between the commit and the draw is answered by that patch, prepared ahead of the draw (`Window::prepare_patch`), instead of a layout pass from the window's root, and the draw finishes it without building the scroller again; a mutation or a scroll write after the read discards it, and a patch gpui declines at the read falls back to a pass. Consecutive commits in a scroller are all patches. Needs the contained relayout patch of the zed submodule, which a window opts in to.
- A row of a virtual list and a root with no root of its own in it are patch roots, so a commit or a hover on a row that declares no hover is a patch frame.
- A hover that only paints (a row that takes another background colour under the pointer) no longer holds a list's scroll as a frame built whole: a wheel over the rows of ghia-bench's mailbox is a translate for 693 of the 720 ticks of its scroll phase (396), and the tick that follows a crossing repaints the row the pointer left and the row it entered where the translate put them. A hover that more than paints, or that a listener hears, is a frame built whole as before. The scroll phase's median is 4.37M instructions a tick (5.56M), its mean 7.14M (7.6M); row crossings are 4.60M (4.62M). `getPatchCounters().scrollPatch` has `hoverAsked` and `hoverMatters`, which tell a wheel whose pointer is not where the frame shown had it from a hit chain that matters. The engine is zed at 6231b52b34: a wheel on a list goes on from where the list is now, and a patch of a row painted in its region does less work.
- A hover after a wheel scroll is a patch frame again, and a step of a list's scrollbar fade is a repaint of the thumb, not a frame built whole. A row that a hover patched during a wheel left an id in the retention bookkeeping that no longer existed and every later hover was declined; on ghia-bench's mailbox the hover after a scroll goes from 0 of 480 ticks patched (crossing median 7.8M) to 18 of 480 (3.5M), and 243.7M to about 120M for the phase. A prepared patch no longer adds a start region for each element of each patched row, so a long run of hovers leaves the registries the size they were.
- The per-element work of a patch is cheaper: a restyle that only paints is judged once for the pair of interned styles it goes between (the border shorthands and the pointer-state refinements were parsed and folded again on every `setStyle`), the scan for patch roots asks the style of each element once, and a patch compares the tape it captured with the recording by what the writes hold, where it compared strings made by `format!` and `Debug`. The zed gitlink brings the shape store's cache of a text's width-independent marks, and `getLayoutCounters()` reads `snapComputations`, `snapCacheHits` and `endReshapeComputations`. On ghia-bench's mailbox the navigate proxy's App median is 32.0M instructions a key (33.4M with the snap cache alone, 36.5M before), and a hover crossing a row costs 3.66M (4.60M).
- A window on macOS draws only the part of the picture that a frame changed (a hover patch, a list scroll, a scrollbar's fade) and keeps the rest. It is always on, with no option and no environment variable. The picture is the same; a patch frame costs about a third of the GPU time on the mailbox of ghia-bench and a frame built whole 8% more. A scene with an effect group or a surface, a transparent window and a window with native views are drawn whole. `TestRenderer` gets `presentFrame` and `capturePartialPicture`. `GPUI_GPU_TIMES=<file>` logs the kind, GPU time and damage of each presented frame.

**Virtual lists**

- A commit that restyles rows and swaps the content of a scroller, a read of layout after it and a programmatic scroll of a `<virtual-list>` (`scrollTo`, `scrollTop = n`) are one draw: the patch the read prepared is finished, the restyled rows are patched where they stand, and the rows are moved by a translate that builds the row that comes in, where the draw was a frame built whole. A write to a list's offset notifies no view, so it no longer discards the patch a read prepared; a frame whose translate declines is built whole at the new offset, as before. A restyled row of a virtual list that the frame shown does not hold needs no patch (a scroll that brings it in builds it with its new style), so a commit that restyles one is no longer `Commit` at the read. `getPatchCounters().scrollPatch.composed` counts the translates that came after a patch in the same draw. Needs the patch-and-translate draw of the zed submodule.
- A programmatic write to a `<virtual-list>` offset (`scrollTo`, `scrollTop = n`) and a wheel that changes which rows show are drawn by moving the rows that stay, taking out the rows that leave and building only the rows that come in, when the rows that come in have a measured size, where the frame was built whole: the picture, the boxes, what is under a point and where a click goes are those of the frame built whole. `getPatchCounters().scrollPatch` counts them (`membershipFrames`, `rowsBuilt`, `rowsRemoved`) and says what held the others whole (`held["Membership.unmeasured"]`, `Membership.unmeasuredOverdraw`, `Membership.settles`, `Membership.disjoint`, `Membership.noBuilder`). Needs the list scroll patch of the zed submodule.
- A list scroll measures the rows of the overdraw that have no size before it is classified, and builds a row that stays but no longer fits where it was recorded in the translate, where either held the frame whole: the keys of ghia-bench's mailbox that scroll the list are one patch and one translate (21 of 22 composed; the App median of keys 2 to 30 is 38.3M instructions, from 44.9M), and the scroll proxy's median is 5.56M (6.85M). `getPatchCounters().scrollPatch` has `rowsRebuilt`. A row built again is in the registries once (what it wrote before is taken out as the build starts, and the page forgets its records as it forgets a row that left), and a frame that kept no row in place settles the rows that left, where their boxes stayed. A patch of an anchor or a row, and the rows that left, no longer expand the replays a registry has not read to replace what they wrote (hover row crossings 4.70M, 4.62M).
- A `<virtual-list>` tells its list the size of a row whose root style fixes it (a `div` with a `height` in px and a width that is in px or fills a block, padding, margins and borders in px, no min or max size, aspect ratio, container block, motion or transition of a size, and states that only paint), so the rows it does not show are no longer built and laid out in a scratch frame to be measured, and a row that comes into the overdraw of a scroll is built once, where it shows. The list checks every row that shows against what it was told (`getPatchCounters().scrollPatch.declarationMismatches`), and `rowsMeasuredByLayout` and `rowsMeasuredByDeclaration` count how the rows were measured. `GPUIX_LIST_SIZES_OFF=1` turns it off for a measurement. `getPatchCounters().deferredSceneRebuilds` counts the patches that left the scene to the translate after them. Needs the zed submodule at `8434d5c7ad`.
- A row of a virtual list is recorded for the travel of a row that shows (three heights of the list plus its overdraw past the clip, where it was half a height), so a scroll that brings a row in no longer builds a second row again where it is for the region of its recording: the navigate proxy of ghia-bench's mailbox builds one row a key and none again, its App median is 36.9M and 36.1M instructions a key (38.5M), and the scroll phase's mean is 5.51M a tick (7.15M). Other scrollers keep half a viewport.
- The root of a virtual-list row hits the style cache: that a row does not lift is a build input said after its style (`stacking::absorb_lift`), not a flag on a clone of its `StyleDesc`, so the row's style is the element's own `Arc` and no `StyleDesc` is cloned per row (50 rows built whole: `styleDescClones` 99 to 0, `styleAppliesReplayed` 414 to 463). A row whose root is a custom element (`<img>`, `<input>`, `<textarea>`, `<markdown>`, `<code>`, `<diff>`, `<svg>`, `<webview>`, `<anchored>`) or a nested `<virtual-list>` is built unlifted as a host root is, so its element and its retained record agree again.

**Building a frame**

- The children plan of a host element (its paragraphs and blocks, and the text a `<text>` reads out) is kept on the element and found again while its subtree, the `white-space` it inherits and the `display` and `order` its `@container` blocks gave are unchanged, instead of planned in every build: 50 rows built whole cost about 55k fewer instructions a row (a column 45.07M to 42.31M a frame, a list 60.79M to 58.05M). The switch is the style cache's (`setStyleCache`, `GPUIX_STYLE_CACHE_OFF`, and `GPUIX_RETAIN_VERIFY` plans again for every kept plan and asserts the two equal); `getBuildCounters()` has `plansKept` and `plansComputed`.
- A div keeps gpui's interactive element state only when something reads it (focus, scrolling, a click, drag or hover listener, an active or hover style, a tooltip), so a plain host div with an id skips three element-state map round trips per frame: 50 rows built whole cost 21k fewer instructions a row, a patched list crossing 3.110M to 2.993M. A mouse press over a plain div no longer asks the window to refresh. This is an engine patch in the zed fork, always on.
- The step that applies a declared style to a host div is kept per interned style and colour and length context, and the next element with the same style has the result laid over its div: 50 rows built whole cost 5.7% fewer instructions (1000.7k to 943.9k a row), a patched list crossing 2.1% fewer. A style that a state, a transition, a motion, an animation, `var()` or the `rtl` mirror produced is applied each time, as before.
- A plain text is one gpui element instead of a wrapper div, an underlay canvas and the glyphs (three drawables, three layout nodes and three dispatch nodes fewer per text), so building a row of ghia-bench's mailbox costs about 190k instructions less (50 rows built whole: 1188.7k to 998.5k a row), a patched hover crossing 10% less and a keystroke of the navigate phase 4% less. Selection, find highlights, the cull outset and the pictures are the same. A paragraph with a ring, an opacity group, a cursor or region hitbox, a focus anchor or an atomic inline keeps the wrapper.
- The bounds of a host element are read by one shared layout probe instead of two boxed listeners, the bounds registry updates a box where it is stored, and a stacking context moves each lifted entry once. A column of 50 rows built whole costs 2.7% fewer instructions (942.2k to 916.7k a row), and `onLayout`, `getBoundingClientRect` and the observers read the same numbers.
- Recording a subtree for retention is cheaper: a retained root keeps its recording state boxed (4 KB to about 100 bytes moved at each phase) and builds its id once, and the tape of a root that is built again is the last build's, emptied in place. Recording a column of 50 rows costs 13% fewer instructions (66.55M to 57.75M); a frame that replays or patches is unchanged.

**Run loop**

- The embedded run loop pump no longer calls `updateWindows` on every tick (AppKit updates the windows once per event itself) and re-arms its two run-loop watches in one `kevent` call: a pointer move costs 2.2% fewer instructions (0.594M to 0.581M).

### Fixes

- `onVisibleRange` of a `<virtual-list>` reports the rows the list shows whenever its scroll position changes. A write (`scrollTo`, `scrollTop = n` and `scrollBy`, an app's keyboard navigation) moved the list without reporting the rows that came into view, so an app that moves a window of rows from `onVisibleRange` stopped following after its first window and the list went blank (after about 52 arrow keys in the mailbox example). A write now reports the range a wheel to the same position reports, once, and a write that leaves the list where it is reports nothing. Dragging the scrollbar thumb or clicking its track reports it as a wheel does (the DOM fires `scroll` for it), and `scrollTo` or `scrollTop` that rests a bottom-aligned list at its end reports the rows it shows, not `[count, count + 1]`.
- `scrollToItem` on a virtual list reports the rows the list shows after the scroll in `onVisibleRange`, as a wheel to that position reports them, where it reported the item and the next. A row near the end reported `[last, last + 1]` while the list showed the last viewport's worth of rows, and the native addon's `scrollToItem` reported nothing. The range is read from the paint of the frame that applies the scroll, after the layout has held the position to what the list can scroll to, so the event comes with that frame and not inside the call.

## 0.12.0

Patch frames reach hover and list scroll: a hover that only paints, a row of a `<virtual-list>`, a wheel over a list and a caret blink are drawn over the frame shown instead of building the page whole. The native build has `window` and `document` globals.

### Breaking changes

- **An app serves the automation protocol on stdin only when `GPUIX_AUTOMATION=1` is set in its environment.** It used to turn on whenever `process.stdin` was not a terminal, so an app started by a harness with a pipe or closed stdin (or from Finder) loaded zod and eventsource-parser and read stdin for nothing. `launch()` sets the variable in the child; a driver that spawns the app itself and speaks the protocol must set it too, and there is no fallback to the terminal check.
- **`enableAutomation` and `installBrowserAutomation` return a promise.** `@ghia/native/runtime` imported the automation client, and with it zod and eventsource-parser, at the top; it now imports it when automation is enabled (stdin is not a TTY, or a browser render), so in the browser `globalThis.gpuix` is set once the client has loaded instead of inside `render()`.

### Features

- In the native build, `window` (the global object itself), `document` (Ghia's document) and no-op `scrollTo`, `scroll` and `scrollBy` are installed as globals by the new `@ghia/native/dom-globals`, which `@ghia/native/host` imports, so every Ghia UI has them; the wasm build runs in a real browser and installs nothing. `addEventListener` and `removeEventListener` on the global object register with both Ghia's window target and the runtime's, so `keydown`, pointer and focus events reach them while `error` and `unhandledrejection` keep working. `isWebBuild` is exported from `@ghia/native/host`: `true` in the wasm build, `false` in the native one. Use it instead of `typeof window`, which is now `"object"` in both. Web libraries such as TanStack Query and Router, whose client code reads `window` and calls `scrollTo`, now run it.
- The test renderer has `captureShownFrame(path)`, which saves the frame that was drawn last as it is: `captureScreenshot` notifies the view and refreshes the window first, so it could only show a frame built whole, never what a patched tick or a frame that moved the rows of a `<virtual-list>` in place drew.

### Performance

**Hover and caret patches**

- A hover that only changes how elements paint (a background colour, a border colour, the colour of a shadow) asks the window for a tick instead of rebuilding the view, and a patch frame takes the tick when it can. The hover of an element is classified as paint-only when its `hover`, `groupHover` or `hasHover` style changes nothing but colours, an opacity that stays a layer, or the colour of a shadow or a border (`events/hover_paint.rs`). A hover that a listener hears (`pointerenter`, `mouseover`, ...) or that changes anything else is a frame built whole, as it was.
- A hover that only changes how an element paints is drawn by patching the frame shown: the roots that hold it (a row, a card, a small control) are built again and gpui writes the primitives they paint over the frame, where the whole page was built. The frame built whole leaves the roots that hold such a hover ready (`retained(..).patchable()` for a root of at most 64 elements that lifts nothing, has no group and no intrinsic size); the preview of a tick takes the hover from the elements the dispatcher left, and a hover on an element no root holds is a frame built whole (`unpatchable.Hover`). A hover that adds or takes away a primitive (a background where there was none) or a group is a frame built whole, as before.
- A hover that gives an element a background it had none of is a patch frame: an element whose `hover` or `hasHover` sets a background colour paints a fully transparent background quad where it has none (gpui's new `Style::keep_transparent_background`), so the quad is in the root both ways and the hover writes a colour over it. The mailbox row of ghia-bench crosses at 4.48M instructions against 8.57M, all 18 crossings patched; the scroll phase pays the quad, 7.89M a tick against 7.64M. The page, the hit test and the pointer events are what they were.
- A row of a `<virtual-list>` is patched where it was recorded: a hover that only paints (a background colour over a background the row already has) is drawn by writing the primitives of the two rows over the frame shown, and no longer by a frame built whole. In the mailbox proxy of ghia-bench with rows that paint a background, a row crossing costs 4.7M instructions against 9.7M (the bench app as it is, whose hover gives the row a background it did not have, adds a quad and is still a frame built whole: 9.3M). A row the list has put elsewhere since it was recorded is a frame built whole (`unpatchable["Hover:Relocated"]`), and the frame after a patch that moves the rows by a scroll is built whole too. The patch compares the operations of a root by their fields where it formatted them (25.7M of a 27.9M tick), and a marker a recording puts elsewhere is no difference.
- The blink of a focused `<input>` is a patched frame that builds the input alone when the page holds a `<virtual-list>`. A virtual list or one of its rows made the frame before it unsteady (`Exclusion::varies_with_time`), so every tick of a loop or caret elsewhere on the page was drawn whole and rebuilt the visible rows (about 2.4 ms a blink in a mail client with a search box). A list is painted as the frame that built it left it, and what changes it afterwards (a scroll, a new window of rows, an animation in a row) is a source of its own, so a tick no longer waits for it.
- A patched tick whose changed operations keep their kind and bounds (a colour loop, a caret blink, a stroke that moves inside its box) writes their primitives over their slots in the scene's typed vectors, instead of replaying the whole frame's operations and sorting every vector again: several million instructions on a 2700 operation frame, whatever the number of operations that changed. The first patch after a frame built whole still makes the scene again, and so does a patch that moves a primitive, clips one away or changes an operation that is not a plain primitive. `getPatchCounters()` has `sceneRebuilds` and `inPlacePrimitives` for it.
- The tick that follows a frame that moved the rows of a `<virtual-list>` in place (the blink of a caret, a transition) is a patch again: the translate left the view the scroll had notified on the queue, so the tick declined for a pending view and was drawn whole.

**Scrolling a `<virtual-list>`**

- The frame drawn after a wheel event over a `<virtual-list>` is not built when the rows only moved: the translates of the classifier are drawn by putting the rows of the frame shown where a replay of their recordings puts them at the new position (the scene, the hitboxes, the boxes `getBoundingClientRect` reads, the regions text is selected from), the scene is made again from its log, the hover is followed as after a drawn frame, and nothing else is walked. `getPatchCounters().scrollPatch` gains `patched` and `applyDeclines` (why a translate that could be made was drawn whole; nothing is written before it declines). `GPUIX_SCROLL_PATCH_OFF=1` or `setScrollPatchEnabled(false)` draws every frame whole as before; under `GPUIX_RETAIN_VERIFY=1` each translate is compared with the frame built whole after it (scene with draw orders, hitboxes, registries).
- `getPatchCounters().scrollPatch` says how the frames drawn after a wheel event would have been drawn by moving the rows of the frame shown: `frames`, `eligible`, `mispredicted`, `hoverOnly` and `reasons` (the first reason a frame was not a translate: `Edited`, `Membership`, `Hover`, `Place`, `Region`, `Clip`, `Focus`, `A11y`, `ScrollAnimation`, `NotRelocatable`, `Other`). It counts the frames that could be a translate by what would change on screen, not by the hitboxes under the pointer: `Hover` is a pointer whose move from one element to another would restyle something (`hover`, a group, `whileHover`, `:has(:hover)`) or reach a listener (`pointerenter`, `pointerleave`, `pointerover`, `pointerout` and the mouse ones, also on `window`), and `HitboxChain` (in `held` only) counts the hitboxes that change under it. A root nested in a row that was built is no `NotRelocatable` run any more, and `held` names the edge a recording leaves bare (`Region.top`, `Region.bottom`, `Region.side`) and why a row cannot be moved (`NotRelocatable.noRun`, `.noRecording`, `.unmovable`). In the mailbox proxy 328 of 720 frames are eligible and none mispredicted (none before).
- The frame drawn after a wheel event over a `<virtual-list>` with the scrollbar the system draws is no longer built either: the translate moves the thumb with the rows (the list's bar tells gpui, through `Window::paint_scroll_thumb`, how a scroll moves its thumb, and the quad is written over the operation it painted, at the bounds the build would paint it at), and starts the second of the bar's hold again as a built frame does. Where the thumb cannot be put there, the frame is drawn whole and says why: `Thumb.size`, `Thumb.alpha`, `Thumb.appear` (the first wheel after the bar faded) and `Thumb.track` in `getPatchCounters().scrollPatch.held`, and `applyDeclines.Thumb`. A frame that moves the rows is also drawn whole when the bar of a scroll container is due a frame (the end of its hold). The mailbox proxy with its default scrollbar patches 328 of 720 frames, as with `scrollbarWidth: "none"`, where it patched none.
- A scroll translate writes the translated operations of each row straight into their places in the frame instead of collecting those of every row into vectors and copying them over, and a translate that declines still writes nothing. In the mailbox scroll proxy a patched tick went from 6.4M to 5.4M instructions.
- The overlay scrollbar asks for no frame while it holds. After a scroll the bar stays whole for a second and then fades over 200 ms; the second used to request a frame at every vsync that painted the same bar and made every tick unpatchable (one `scrollTo` was 70 to 140 frames built whole, most of the cost of an ArrowDown through a list). One timer on the window's clock now waits for the end of the hold and only the fade asks for frames. A bar under the pointer or a held thumb asks for none while it is steady either, and a tick (a caret blink) in the hold is a patched frame, as is the blink of an input beside a list that was scrolled. A tick that finds a bar painted at an alpha the clock has since changed is still drawn whole. A virtual-list row that the pointer had been over no longer keeps the page from patching: its hover left it in the set of elements no build had entered, so every blink beside a list under the pointer was a whole frame.
- A scroll write (`scrollTo`, `scrollTop = n`, `scrollLeft = n`) no longer lays the page out. It used to read the scroll metrics first and then draw a pending change, so a write after a mutation was a whole layout pass and the frame after it drew the page again (4 passes an ArrowDown and 2 a typed key in a mail client with a search box, 12 to 17 million instructions each). A write made while the layout is older than the tree is recorded and made by the layout that comes next, which clamps it, as a browser does; one with nothing pending clamps at once, as before. A `div` scroller written to another vertical position than the start while the layout is behind still lays out first, as scroll anchoring needs the DOM's order. `scrollTo({ top })` names one axis to native, which keeps the other. A read (`scrollTop`, `scrollHeight`, `clientHeight`) lays out only when a layout-class change is pending, so a write followed by a read still returns the clamped value. A smooth scroll and a write to a scroller mounted since the last render lay out first too.
- The rows of a virtual list are retained: a row that did not change is skipped and one the list scrolls by is moved, where every frame built every visible row. Only the changed row and the list around it are built. In the mailbox bench proxy a key (ArrowDown in a 10 000-message list) takes 52M instructions instead of 63M and builds 125 elements instead of 259; a chat page of `retain.perf` skips 92% of its elements at idle instead of 59%.
- A windowed `<virtual-list>` whose `itemCount` goes down keeps its list state: the heights measured so far, the scroll position and the focus handles stay, and only the rows at the tail are dropped, so the rows in view are no longer measured and laid out again on every change, and the work is as large as the drop and not as the count. A count that goes up still makes a new state, because gpui gives a spliced-in row no height hint (see `list_resize.rs`). A rebuild also skips a pass over every row that made no change.

**Scene and draw order**

- Putting the operations of a recording back into the scene (the replay of a retained row, a scroll translate, and the scene made again from its log after a patch) copies each primitive twice and no more, and works out its window bounds once. It used to clone it for the log, move it through `insert`, `record` and `route`, and clone it again for the typed vector (about eight copies of the 240 bytes of a glyph sprite). In the mailbox scroll proxy a frame replays about 2700 operations, and a tick went from 12.4M to 9.8M instructions.
- A primitive of a recording that is put in the frame (a row built before it is shown, a row moved by a scroll translate) is copied once into the slot the log keeps it in and moved there, and no longer through a temporary and several moves: the 328 patched ticks of the mailbox scroll proxy cost 3.60M instructions against 4.08M, the ticks built whole 11.99M against 12.26M. A frame patched by a scroll translate or by a patch whose operations moved makes its scene again from the log it already has and no longer copies every primitive into a second log: the 328 patched ticks cost 4.09M instructions against 5.07M, and the scroll mean 8.54M against 9.06M.
- The scene a relocatable row is recorded in is kept for the next row, with the room its vectors grew to, instead of being made from nothing and grown by doubling in every frame that builds a row.
- The scene sorts its sprites by draw order and atlas texture, stably, and moves each primitive once instead of sorting the primitives themselves: a frame of 2000 glyphs spent a sixth of a rebuild in that sort. Sprites of one order never overlap, so which is drawn first is not seen, and the renderer batches by texture as before. The primitives of a frame are sorted as one number each instead of a tuple of structs (the 328 patched ticks of the mailbox scroll proxy cost 3.26M instructions against 3.60M, the ticks built whole 11.61M against 11.99M, the hover row crossings 8.60M against 9.12M), and by a sort that finds the sorted runs they come in (a row of a list at a time) and merges them (3.12M against 3.26M, the ticks built whole 11.37M against 11.55M). Owner-approved engine change (docs/fork/syncing-upstream.md).
- Draw orders cost less to work out: gpui's bounds tree checks the last 16 bounds it was given before it searches, and stops at one that encloses the new bounds, as a row's background encloses its text. The orders are the same. The scroll of the mailbox app of ghia-bench takes 7.50M instructions a tick against 7.87M, its patched ticks 2.93M against 3.37M, and a row's hover background no longer costs anything in a scroll.

**Memory, startup and the run loop**

- Lower memory. A CSS length is stored as one term (or a shared array for a mixed-unit `calc()`), so a style takes 6.3 KB instead of 16 KB; a Motion state's tracks are boxed; and an image tile over 512 px gets an atlas texture of its own size. At rest, with the Solid transform cache warm: the ghia-swiftui demo 131 to 116 MB, its Apple Music clone 260 to 211 MB, the fluid-functionalism gallery 195 to 178 MB (measured with a 256 KiB instance buffer start that was reverted afterwards: up to 5 MB less than a build now).
- The scene kept for the next relocatable subtree (a row of a `<virtual-list>`) is cleared once the row's recording has been taken from it: it held the primitives of the last row, their path vertices and the pixel buffers of surfaces among them, alive until the next relocation.
- An app that does not turn automation on no longer loads zod (about 1.8 MB of heap).
- Input wakes JS once per event on macOS 26 and later. AppKit begins a Core Animation transaction for every event it sends, and its update cycle committed one that began before the display's next frame boundary from a timer at that boundary, which woke JS for a tick that did nothing else. The pump now commits it right after the event. Mouse moves over ghia-bench's Mailbox at 120 Hz: 1.03 to 1.09 wakes per move against 1.46 to 1.88, about 140 process wakeups a second against 185 to 230, and 4 to 12% fewer instructions per move.
- The window title is given to the platform window when it changes, not on every frame. `GpuixView::render` called `Window::set_window_title` each time, which on macOS is an AppKit `setTitle` and an accessibility update per painted frame of a scroll. The view now keeps the title it last set and sets it again only when `setWindowTitle` (or the first render) gives it another.

**Solid**

- Solid no longer queues a `setStyle` or `setCustomProp` for a value the element already has. An effect that ran again and built an equal style object (a row whose style reads `selected`, an `aria-label` and a style in one effect) sent the whole style to native every time: in the bench's mailbox app, 180 identical `setStyle` ops and 27 KB of JSON for a key that changed nothing. The host remembers the JSON it last wrote for each element's style and custom props and writes only what differs from it, so a style object changed in place and passed again is still written, and so is a key order that differs. A prop never written is written, and a new native element starts with nothing written. `@ghia/native/host` exports `SentWrites`.

### Fixes

- The test renderer's `drawFrame()` covers every batch applied before it. A key handler that read layout and then applied one more batch left a notify owed after the frame, and the next simulated input redrew the unchanged page: one extra painted frame and about 18M instructions per key in the mailbox bench proxy.
- A `backdropFilter` blurs the content painted after a `<nativeview>` or `<webview>` that is under it. The filtered backdrop went over the layer above the view, which starts out transparent, instead of replacing what the layer held under the box, so the sharp content showed through the translucent blurred copy and the blur read as nothing. It now replaces it, on a transparent window too.
- `:focus-visible` after a script focus (`focus()`, `autoFocus`, `focusElement`) now follows Chrome. It used to inherit the visible state of the element focus left, plus "no input yet"; Chrome keeps two window-wide facts instead: a mouse press that moves focus marks it as the mouse's and clears the last key, a key down (Shift alone too, not Ctrl, Alt or Cmd) sets the key, and a script focus changes neither. So a script focus now shows the ring after a press on blank body, and after Tab then a click on blank body, and no longer shows it when a text field was script-focused after a click.
- `:focus-visible` (`focusVisible` and `hasFocusVisible`) no longer depends on `transition`. An element with any `transition*` ignored the focus ring when a script focused it before a key was pressed (autofocus, a dialog's first focus, `focusElement`), and a text field focused by a click lost it too, because the transition path read the window's last input device instead of the focus state the element without a transition uses. A `focusVisible` style on a transitioned element now matches in the same cases as on a plain one, and still transitions in.
- A window with native views no longer grows while it draws: the published addon kept a record of every composed frame (about 2.4 MB per 1000 frames on the Apple Music clone). The GPUI layers above a native view share the window's pipelines and command queue, keep two drawables instead of three, and hold none while they have nothing to draw. A transitioning element with no state style to fold no longer copies its style.
- A node Solid removes is out of the native tree at once, as `removeChild` takes it out of the document, and a layout read in the same turn no longer lays out the removed subtree. The host used to detach it on the JS side and tell native only at the flush, so `getBoundingClientRect` or `scrollHeight` right after a keyed `<Show>` swap built and laid out the old subtree beside the new one (the mailbox navigate proxy: a detail scroller with twice its children in the pass, 56 elements built there for 40 now). `removeHostNode` now queues a new `detachChild` op, which takes the element out of its parent and keeps it, with its state, for an insertion that puts it back; the element is still destroyed at the flush if it stayed out.
- A wheel event over a `<virtual-list>` in the draw of a tick is drawn whole: a translate builds nothing, so it took the tick (a CSS transition, a keyframe animation, a motion value, the blink of a caret) and nothing asked for the next frame, and what followed the clock stood still until a frame was built whole. The frame is `Clock` in `getPatchCounters().scrollPatch.reasons`, for a tick requested for the draw or a last frame that asked for another, and the translates resume when nothing runs.
- The frame drawn after a wheel event over a `<virtual-list>` is built whole when a source other than the scroll differs from the frame shown (a press that restyles with `:active`, the focus, a selection, a measurement, a link, a command, a custom element): they notify the view with the entity the list notifies with, so the tree and the queue of views could not tell them apart and the translate left them out of the picture until the next frame built whole. The gate compares the sources as a tick does and says `Edited` (`getPatchCounters().scrollPatch.reasons`).
- The thumb of the scrollbar of a `<virtual-list>` is moved back by a translate that returns the rows to where the last whole frame painted it: the translate compared the new place of the thumb with the whole frame's and left a thumb that an earlier translate had moved on its other pixel.
- An `IntersectionObserver` (and `onLayout`, `ResizeObserver` and `content-visibility: auto`, which read the same boxes) is swept after the frames that move the rows of a `<virtual-list>` in place, as after a frame that built them: the sweep was a canvas that only a painted frame runs, so a row that a translated frame brought into view was not told of until a frame was built whole.
- `onVisibleRange` of a `<virtual-list>` fires when the visible range changes, not on every scroll event. A scroll that stays within the same rows (a 30 px wheel tick over 72 px rows) reported the same `startIndex` and `endIndex` again, a native-to-JS event and a handler call for nothing; the list now keeps the range it last reported and reports a different one. The first scroll still reports its range, and `scrollToItem` still reports its own.
- Fixes taken from upstream GPUI. A window with `windowBackground: 'blurred'` is blurred on macOS 27 again. Translucent layers composite with the right alpha over a transparent target: two half-transparent boxes that overlap no longer add up to an opaque one. A cached view follows a change of the opacity it inherits and keeps its subscriptions to the entities it read when it is reused. The cursor no longer reverts when a drag starts, because it is resolved after the listeners of every mouse event. A synthetic drag stops after the button is released. The menu key equivalents of backspace and delete show their glyphs. Two panics are gone, one for a released atlas texture and one for a hit test past the end of a wrapped line. The accessibility adapter is released when its window closes, and the text system no longer leaks.

## 0.11.1

### Breaking changes

- **`<nativeview>` `onAttach` runs inside the frame that makes the surface, and can no longer call Ghia.** It runs in the frame's prepaint, with a content view that already has the size of the element's padding box, instead of one event-queue turn after the frame. The view a library adds there is in its container when the frame places it, and the frame presents the view and the GPUI content around it with one Core Animation transaction, so a new glass view no longer shows for a frame before or after the content above it. Like `onDetach`, `onAttach` can no longer call gpuix (a renderer call from it fails with the nested-call error) and the state it writes is a later batch: children that wait for `onAttach` show a frame after the view, so a library should render them from the first frame. Where native cannot call JS from inside a frame, `attach` is still queued.

### Features

- A window opened with `GPUIX_BACKGROUND=1` in the environment emulates focus, as Chrome does with CDP's `Emulation.setFocusEmulationEnabled`: it behaves as active for `onFocus`, `onBlur`, `:focus-visible`, the caret and `focusElement`, without becoming the key window or activating the app. Until now a window opened behind other apps (`focus: false`) fired no focus event and drew no caret while typed text still arrived. A window without the variable is unchanged: a window that is not active fires no focus events, as in Chrome, and they fire once it is activated. The library reads the variable once, when the window opens; apps that map it to `focus: false` keep doing that.
- `kind: 'panel'` in the window options opens the window as a non-activating panel: a normal window (titlebar, resizing, buttons, appearance, background, normal window level) that can be the key window without activating the app. With `focus: true` it is key while the frontmost app stays frontmost, so a capture can show the key look (glass tints, accent colours, traffic lights) that a `focus: false` window never has. `renderer.isWindowKey()` reads whether AppKit reports the window as key. An unknown `kind` throws; `'normal'` is the default, and on Windows and Linux a panel is a normal window. A panel takes the keyboard like any key window, so open one only for a capture and close it right after.

### Performance

- A page with a `Reorder.Item` (a `layout` box with `dragOffset`) beside a looping animation patches the loop's ticks while nobody holds the item, as it does without the item. Until now every tick was drawn whole for as long as the item existed. While an item is held, its ticks are still whole frames.
- A page that moves every root in each frame without a scroller doing it (a pan whose offset is a style) no longer pays for skipping roots it cannot replay. Retention judges each frame by what gpui replayed and what it had to build late, and while skipping loses it records and skips only a sample of the roots, coming back as soon as the sample replays again. The timeline pan with culling on costs 16 ms a frame instead of 21.5 (14.4 with retention off), and 243 ms instead of 400 with culling off. Pages whose frames replay well are unchanged. `GPUIX_RETAIN_GATE_OFF=1` turns the gate off, to time a run without it.
- An app with a `<webview>` no longer wakes JS 4 times a second at rest: WebKit's own wake-ups of the main run loop reach JS (2 to 5 wakes in 15 s at rest instead of about 63), and the events of a load, a page-set title and the result of `executeJavaScript` arrive in 1 to 9 ms instead of 5 to 75 ms. On a macOS version whose `CoreFoundation` is not the one this was checked against, the 250 ms timer is used as before.

### Fixes

- A blurred `box-shadow` on a box under an `opacity`, `filter` or `mask` ancestor is no longer cut off at a hard rectangle while the ancestor animates or holds its effect. The group's bounds and the draw order now count the whole blur: an outer shadow reaches three times its blur radius past its box, as it is drawn. The shadow paints as the same shadow with no ancestor effect.
- `dragBy`, `dragTo` and `mouse.drag` drive a drag on a live window when the app drives its own renderer in-process (`connectTest(liveRendererAsTest(renderer))`). The live renderer delivers a press and a release to the page at once but a move only on a later turn of the event loop, so a drag stepped in one synchronous burst reached the page as press, release, then the moves, and a handle that ends its drag on `pointerup` never moved. `liveRendererAsTest` now waits one event-loop turn after every input it simulates, and `TestAutomationRenderer`'s input methods may return a promise.
- A `<nativeview>` under an ancestor with `opacity`, `filter`, `mask` or `clip-path` now fades with the ancestor and keeps its children above it: the ancestor's effect group is split at the view, so the box is composited below the view and the children above it. The view takes the product of the opacities of the groups around it, a filter group's included.
