# Direct paint

An experiment, off by default: a plain host subtree is drawn by one gpui element that owns the nodes of the subtree, where each host would be a `Div`. It measures what removing the commit-to-`Div` translation gains on top of retention. Switch: `GPUIX_DIRECT_PAINT=1`, or `setDirectPaint(true)` on the test renderer; process wide and read at every build, so a subtree recorded before the switch changed is replayed as it was recorded.

The code is in `packages/native/src/render/`; `renderer.rs` has the one branch in the host arm of `build_element_unpumped` that asks `render::is_direct_root` and calls `render::build_direct` instead of `build_host_container`.

## What is built

A direct root resolves the style of every node it holds as the `Div` path does, in the same order and with the same inherited state (`Inherited::descend`, `style_cache::apply`, font features, direction, `position: static` by default), and keeps the result as a gpui `Style` in an arena (`render/node.rs`). Texts and paragraphs are built by the same `text_content` and `paragraph_content`, and are children of a node as they are of a `Div`. `DirectRoot` (`render/element.rs`) is the element: it requests one layout node per host in post order under the text style of its parent, prepaints with the text style, the hit mask of the overflow and the hitbox of each node, and paints with `Style::paint_box_with_effects` and the exact content mask, the calls `Div` makes.

A direct root is culled by its parent like a `Div` (`cull_outset` is what `build_host_container` gives `cullable`, none for a box placed by its containing block), and inside it a text is culled as a `Div` culls its children (`prepaint_unlifted_child`, restated in `render/element.rs` over `Window::lies_outside_the_mask`): a text outside the clip is prepainted as a culled subtree and draws nothing. A retained root that the reference build of `GPUIX_RETAIN_VERIFY` wraps is not culled by its parent and relies on that check, or its out-of-clip glyphs differ from a patched frame's.

The root keeps its entry in `Retain` and its `Retained`/`Taped` wrappers. A node below it has no entry: it leaves `Retain::unbuilt` (`direct_descendant`) so the spine does not hold the elements above it, and it counts in the size of the root, which is what decides whether a root is worth skipping. Everything an entry would have recorded for a plain node is recorded by the root or is nothing (see below). `getBuildCounters()` has `directRoots` and `directNodes`.

## What is direct

`render/eligible.rs`. A root is direct when the switch is on, the window's a11y is off (a direct node registers no accessibility node), and the root and everything it builds is plain:

- Types `div` and `text`, no custom prop, no focus, no `testId` beyond the locator. No listener below the root; the root may have them (`onClick`, `onPointerMove`): the pointer, wheel and click events are the dispatcher's, which runs them along the retained tree, and a host builds nothing per listener when the window has no screen reader (`build.rs` `note_listeners` does what the build of a `Div` does for it: the click path in the key of the root, the clip origin of an intersection listener).
- `position` is `static`, `relative` or `absolute` with `z-index: auto` (see [lifting](#lifting-and-positioned-nodes)). An absolute box needs a positioned ancestor at or below the root (`eligible.rs` `Verdict`), since a retained root can only be kept if the box that places it is in it.
- No `sticky` or `fixed` box, stacking context (`opacity`, `filter`, `mask`, `clip-path`, transforms, `z-index`) other than the root's own (see [stacking contexts](#stacking-contexts)), `visibility`, `app-region`, scroller the user scrolls (`overflow: scroll` or `auto`, or `hidden` on one axis, which computes the other to `auto`; `hidden` on both axes is admitted, see [scroll containers](#scroll-containers-overflow-hidden)), container query or unit, `content-visibility`, custom property, transition, animation, text decoration or `text-box`; `display` is block, flex or grid.
- Below the root, no pointer state or group either. The root may have them: the build folds them in and the root has the hitbox that tells them.
- Children that are blocks, paragraphs of text and plain spans, and empty lines; no atomic inline, table box or `display: contents`.
- The context is plain: not a stacking root other than the row of a virtual list, not an atomic inline, inside an `inert` or `visibility: hidden` subtree, a right-to-left one, a collapsed table, a highlight or a query container.

What a subtree is does not depend on what is above it and is remembered by the revision of the element; what it inherits is judged at the root.

## What a direct node has

Each node does what a `Div` host does for the pointer and for the bounds registries, in the same order, with its state in the arena node (gpui moves an element's own prepaint state by value, so nothing per node lives there).

- **Hitbox.** `prepaint_node` pushes the host element id of the node (`Window::with_id` along the arena, as the id stack of a `Div` has it, which is what names the hitbox: `host_hit_chain` maps the hit to the descendant, so the `target` of an event is the node under the pointer and a `composedPath` has the nodes between it and the root). A node gets one where `Interactivity::should_insert_hitbox` gives a host that is not a text node one: the window has DOM hit testing on, the node is `pointer-events: none` (the hitbox is then `PassThrough`, only a link in the chain of a descendant that is hit, and `auto` below it reopens), or it has a cursor. Its shape is the border box with the corner radii of the style (`border_box_radii`, which gpui keeps to itself, is restated in `element.rs`), and its children are prepainted under `with_hitbox_parent`.
- **Cursor.** Paint calls `set_cursor_style` with the hitbox, unless the platform has a drag in flight (files dragged in from outside), where a `Div` sets none.
- **Bounds.** What `HostBoundsProbe` does for a `Div`, shared in `automation.rs` (`read_layout`, `paint_host_bounds`, `publish_host_bounds`, `host_bounds_flags`): the box is read where layout left it in prepaint; paint notes the layout node and records the box (and the start region of a node that declares `user-select`); a pass that does not paint (a read, a patch prepared ahead) reports the box from prepaint through `Window::publish_layout`, and a culled node does both as a `Div` in a culled subtree does. `getElementBounds`, `getBoundingClientRect` and the observers see a direct node as a host.

- **`user-select`.** A node that declares it claims a selection-start region as a `Div` host does: `host_bounds_flags(selection_start_flag(style))` in the node, written by `paint_host_bounds` in paint (on the tape of the root, so a replayed or patched root carries it) and not in a pass that only lays out. What the nodes below it inherit is the build's: `Inherited::descend` sets `selectable` per node in `build_node`, and `text_content` and `paragraph_content` hand it to the text they build, so a drag, `getSelectedText` and a copy see the text a `Div` build would give. A subtree that is `inert` is not direct, so the inert cases of `build_host_container` (a start region that is never selectable, `user-select: text` that does not reopen it) do not arise.

`Window::note_publication` is called before the layout sample and before the paint of the box, as a `Div` calls it before it hands the probe a sample, so a recording that holds the boxes of direct nodes is counted as one that publishes.

## Scroll containers (`overflow: hidden`)

`overflow: hidden` on both axes is a scroll container that only code scrolls (`scrollTop` works, the wheel does not), and a node that has it is direct. The handle is the one the host has in `scroll_handles` (`scroll::scroller_handle`, which `apply_container` uses too), the style is `scroll::scroll_container_style` over the refinement (the axes that have an offset are `scroll`), and the nodes below the root run the same scroller code as a `Div` through helpers in gpui that `Div` calls itself (`ScrollHandle::note_scroller_layout`, `ScrollHandle::begin_scroller_prepaint`, `ScrollerFrame::clamp_scroll_position`, `Style::lay_out_without_scrollbars`; zed `a141c8ba4d`, no behaviour change for a `Div`):

- **Layout.** The node is requested with the axes that only code scrolls laid out as `hidden`, and tells layout that it may anchor its scroll position.
- **Prepaint.** Before the node is read, the handle gets the boxes of its children and measures the range of its content and its scrollport from layout; after its hitbox (a scroller always has one) the offset is clamped to the range, anchoring steps it, and the box and range are recorded for the handle and for the patches of the frame. The children are prepainted under the clamped offset (`Window::with_element_offset`), a culled node does the same, so `scrollTop`, `scrollHeight` and `clientHeight` read back as for a `Div` and a frame that replays or is patched moves the content with the handle.
- **Build.** `scroll::note_scroll_container` tells `Retain` what `build_host_container` does (the offset is part of the key; the container the children are built in), and `Retain::scroll` folds the offsets of the scrollers below a root into the root's record, since they have no entry of their own: a scroll from script makes the root a change, and a root that holds a scroller is no patch unit, as an entry with one is not.
- **Bounds.** `host_bounds_flags` carries `scrolls`, so the layout sample of the node has the size of its content (`scrollWidth`, `scrollHeight`) as for a host with a handle.

A node that has an `onScroll` listener is not direct (the reporter is made by the build of a `Div`), and neither is one the user scrolls: `overflow: scroll` and `auto` need the wheel, scroll chaining and a scrollbar.

## Lifting and positioned nodes

A positioned box (`relative` or `absolute`, `z-index: auto`) is not drawn in its place in the tree: the stacking context around it takes it (`Element::lift_z`) and paints it above the in-flow content, and an absolute one is placed by the clip and offset of its containing block, not its parent's (`Element::escapes_to`). A `Div` child does this through gpui's elements, so a positioned node of a direct root is an element of its own: `DirectRoot::positioned`, the same type as the root, over the same arena (`Rc`), walking the nodes below its node. The node is a `Child::Positioned` of its parent, whose walk makes the element in layout and handles it as `prepaint_child` of `Div` does:

- **Prepaint.** When the window is lifting (`Window::lifting`) and the node has a `lift_z`, `begin_lift`, prepaint the element, `finish_lift` with it; the ordinal is kept in the walk that made the element, and paint skips the node with `mark_lifted(ordinal)`. Otherwise the element is prepainted as an unlifted child, culled as a `Div` culls it (`prepaint_unlifted_child`: never one that escapes or lifts).
- **The frame.** The children of a positioned box (and of one with layout containment) are prepainted inside `Window::with_frame`, which is what an absolute descendant is placed by; the clip of a node is painted with `Window::with_overflow_clip`, with `escape_inside` read from `Window::escapes_prepainted` around the prepaint of the children, as `Interactivity` does.
- **Placement.** `lift_z`, `escapes_to` and the frame come from the refinement of the node's style (`StyleRefinement::lift_z` and `escape`, which `Style` does not have: a resolved `Style` has `lifts: true` by default), kept in `Placement`. The root reports its own, so a `Div` parent lifts a positioned root.
- **The element id stack.** The element of a positioned node is checked against the ids on the stack when it was made in layout, and a `Div` has them in every pass, so every node below the root pushes its host id in layout, prepaint (culled as well) and paint (`Walk::on_path`, `in_scope`).
- **Retain.** A positioned descendant has no entry, so the root tells `Retain` that it lifts (`direct_descendant(id, lifts)`: `Record::lifts`, as a descendant entry with a `lift_z` would). The `lift_z`, containing block and context of the root itself are recorded as for any host.

gpui's `Window::lifting`, `begin_lift`, `finish_lift`, `mark_lifted`, `LiftTicket`, `with_frame`, `with_overflow_clip`, `escapes_prepainted`, `lies_outside_the_mask` and `note_publication` are pub for an element that prepaints its descendants itself (visibility only; zed `3c03f1e0c6`).

## Stacking contexts

Only the root of a direct root may form a stacking context, and it is one in two cases: it is the row of a `<virtual-list>` (a stacking root, `stacking_root` and `is_virtual_row`, and `lift_absorbed`: its style says it hands nothing to the context around the list, which prepaints a row in a lift barrier), or its style makes it one (`z-index` on a positioned box, or on a flex or grid item): `layout::stacking::forms_context`, the one function `build_host_container` flags its `Div` with, is asked in `build_direct` and the answer is `Placement::context` of the root node. The root of the page and the root of an atomic inline stay `Div`s. A descendant that forms a context (a `z-index`, `opacity`, a transform) is not direct, so a context is never nested in a root; one that is a root of its own (its parent being a `Div`) is direct with a context of its own when it has a `z-index`.

The node does what `Div` does around its children, through two pairs of calls in gpui that `Div` makes itself (zed `1fdf59848e`, no behaviour change for a `Div`):

- **Prepaint.** After the hitbox of the node and inside the positioned frame, `Window::begin_stacking_context` (which notes where the hitboxes of the children start) before the children are prepainted and `end_stacking_context` after, which puts the hitboxes of what was lifted where hit testing finds them (the negative ones under the in-flow children's, the rest over them) and returns the lifted elements in paint order (`StackingLifts`, kept by the `DirectRoot` and emptied by a culled prepaint, as `Div` empties its own). `Window::lifting` is read after it begins, so the positioned nodes below hand themselves to this context, and not to the one around the list.
- **Paint.** The children are painted inside `Window::paint_stacking_context`, which paints the lifted elements with a negative `z-index`, calls for the children (each lifted one is skipped with `mark_lifted`), and paints the rest, with the tab stop bookkeeping of the context.

The record of the root in `Retain` is the one a `Div` root has: `stacking` and `lift_z` are recorded by `build_element_unpumped` before the root is built (a row is a context and has no lift), and `direct_descendant(id, lifts)` tells it that a positioned descendant lifts into the context, as an entry would.

## Layout scope

The layout engine keeps a node from frame to frame by the scope of its request and the number of the request in that scope; a `Div` is its own scope (the hash of its element id path, set by `Drawable` around its layout and prepaint). A direct node is not an element, so under the scope of its root the nodes of a root were numbered by their order in it: a node inserted or removed before another gave the other its number and its layout node. Scroll anchoring follows a layout node (`ScrollAnchoring` keeps the `LayoutId` of the anchor), so a scroller whose rows were nodes of one direct root anchored to the row that took the place of the anchor, not to the anchor (the offset moved by one row too little, or too much). Every node below the root now makes its requests in a scope of its own, as a `Div` does: `Window::with_layout_scope_of(host id, ..)` (zed `with_layout_scope_of`, which pushes the id and sets the scope from the id stack; the hash is `GlobalElementId::scope_hash_of`, which `GlobalElementId::new` shares), in layout, prepaint and culled prepaint (`Walk::in_scope`). A node that is a scroll anchor, a retained layout node or a keyed measured text keeps its node when its siblings come and go.

## What a direct node does not have yet

No accessibility node, no element state, and no listener, focus or scroller the user scrolls of its own below the root, no stacking context below the root, and no sticky or fixed box. A subtree that needs one of those is not direct. See [deviations.md](deviations.md#direct-paint).
