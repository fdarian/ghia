# The web renderer and the Vite toolchain

The UI process of a Ghia app is a web renderer, like an Electron renderer or a React Native app: it has the globals a web page has, it resolves packages to their browser builds, and server code runs behind an RPC boundary. `ghia` (the `ghia()` plugin, `dev()` and `build()`, and the `ghia dev` / `ghia build` commands, a thin Effect CLI over them) `@ghia/solid/vite` and `@ghia/react/vite` carry that into the toolchain. This file records why it is built this way; what an app author does is in [docs/solid.md](../solid.md) and [docs/reference.md](../reference.md#window-and-document).

The reason is the principle in [index.md](index.md#the-principle-dom-and-css-semantics): code written for the web works unchanged. The libraries a web developer reaches for (TanStack Query and Router, `nanoid`, `solid-js/web`) pick their build from `window` and from package export conditions, and a UI process that looks like a Node server gets their server builds.

## The renderer behaves like a page

- **`window === globalThis`.** In a page `window` is the global object, and in React Native the global is aliased the same way. Anything that stores state on `window` or compares to it works. The native build sets `globalThis.window = globalThis` and `globalThis.document` to Ghia's `document`.
- **Listeners go to two targets.** `globalThis.addEventListener` and `removeEventListener` register with Ghia's window target (`packages/native/js/events/window-target.ts`) and with Bun's original methods. Ghia's target is what turns the native event types on and dispatches `keydown`, pointer and focus events. Bun's keeps its own `error`, `unhandledrejection` and `message` events working. Each target dispatches only its own types, so no listener runs twice. `dispatchEvent` stays Bun's.
- **`scrollTo`, `scroll` and `scrollBy` do nothing.** Ghia has no document scrolling element, so the viewport cannot scroll, which is the DOM behaviour of a page that does not overflow. TanStack Router calls `scrollTo` on every navigation.
- **Nothing else is installed.** No `location`, `localStorage` or `innerWidth`. A missing API throws, which is the loud failure we want; a stub would hide the gap from the app that depends on it.
- **The browser (wasm) build installs nothing,** because it runs in a real page. `isWebBuild` from `@ghia/native/host` tells the two builds apart; `typeof window` can not, since the native build now has a `window` too.
- **Where it is installed.** `packages/native/js/dom-globals.ts`, exported as `@ghia/native/dom-globals`, is idempotent. `host.ts` imports it, so every Ghia UI has the globals, and the Vite plugin makes it the first import of the app entry, so a library that reads `typeof window` while it loads sees them.

## Vite, not Bun flags

Bun has no way to resolve packages like a browser. Measured in the renderer spike:

- **Bun always matches the `bun` and `node` export conditions.** `--conditions` only adds conditions, so the first matching key in a package's `exports` still wins, and a package that lists `node` before `browser` loads its server build.
- **`--conditions=browser` selects `@ghia/native`'s wasm build,** because its `exports` has a `browser` entry. The addon is unusable under the flag.
- **The flag is process-wide.** A Worker inherits it and cannot opt out, so it can not give the UI browser builds and server code Node builds in one process.
- **A runtime plugin cannot do it.** In Bun 1.4.4 `onResolve` is never called for bare specifiers. The `onLoad` swap that Ghia's preload used is a per-file allowlist (each package with a server/browser split needs an entry) and applies to the whole thread.
- **`Bun.build({ target: "browser" })` works for a bundle but gives no dev loop,** no HMR and no way to run the app from source.

Vite gives each environment its own resolution. `ghia()` defines a `ghia` environment with `consumer: "server"` and `createRunnableDevEnvironment`, so a Vite ModuleRunner imports the app inside Bun's own process. The conditions are `browser`, `import`, `module` and `default`; under vitest they are those plus every condition another plugin added (vite-plugin-solid's `solid`), minus vitest's own `node`. `consumer: "client"` does not work in a runner: it injects the browser HMR client (a WebSocket that fails), and gives no dependency externalization. Libraries that ship JSX source (`@tanstack/solid-router`) are compiled with Ghia's options too, through vite-plugin-solid's `solid` condition, which the preload could not do for `node_modules`.

What it costs, from the Vite spike (headless, Bun 1.4.4): a warm start to the first render was about 580 ms against about 207 ms for the preload, and an HMR update about 76 ms (bimodal, 20 or 120 ms) against about 92 ms for `bun --hot`.

## Only the addon stays external

Everything else is bundled (`noExternal: true`): `@ghia/solid`, `solid-js`, `@ghia/native/host` and the rest of the native package's JavaScript. Two copies of Solid break reactivity: a bundle that left `@ghia/solid` outside got its own client `solid-js` while `@ghia/solid` loaded another, and signals set in app code were never tracked by the renderer. So the app and the adapter share one `solid-js`, and `solid-js` is deduped.

Only `@ghia/native` is external, with its subpaths (`external` is a prefix match). The addon has to load as a real module, and externalizing the package keeps its `browser` export, the wasm build, from being picked. Consequences: there is one native instance, `dist/main.js` resolves `@ghia/native` from `node_modules` at run time, and an app lists `@ghia/native` as a direct dependency because the injected `dom-globals` import resolves from the app.

`solid()` adds solid-refresh itself, for `ghia dev` and for files outside `node_modules`. vite-plugin-solid treats a `server` consumer as SSR and does not add it, and an edit would reload the whole app. `solid()` also skips the `server` environment below, which has no renderer.

## Server code runs in a Worker

The UI thread draws frames, so server work that blocks it stalls the window. The decision is a Bun Worker behind an RPC boundary, with a separate process as the option for crash isolation. The numbers are in [docs/solid.md](../solid.md#why-a-worker): a Worker starts in 7 ms and adds 8 MB inside the UI process, a separate process starts in 24 ms and holds 22 MB idle, and a 500 ms server task stalls an in-process call for 499 ms and the UI by 0.3 ms from a Worker. A Worker shares the UI's address space, so a native crash takes the window with it; that is the price, and the process is the way out.

- **Ghia owns the Worker and the port, not the RPC library.** `serve(port: MessagePort): () => void` is the whole contract: wire a handler to the port, return what detaches it. oRPC's MessagePort adapter is the documented template and nothing in Ghia imports it. oRPC's `upgrade()` returns nothing and never removes its listeners, so the template passes it a port wrapper whose listeners hang on an `AbortController`.
- **The server is a second Vite environment,** `server`, with Vite's server defaults: Bun/Node resolution, `node_modules` external, no browser conditions and no `dom-globals`. The Worker runs its own ModuleRunner, whose transport is the Worker's message channel (as Cloudflare's workerd runner does), so the server graph resolves with its own conditions.
- **A server edit reloads the server on the same port.** The Worker calls the previous cleanup, clears the runner's cache, imports the entry again and calls `serve(port)` with the same port. Restarting the Worker would have needed a new port and a new client in the UI. A call in flight at that moment can go unanswered, which is acceptable in dev.
- **The UI's end of the port reaches the UI through a slot on `globalThis`** that `virtual:ghia/server` reads before the UI entry loads (dev), or through a `MessageChannel` and `new Worker(new URL("./server.js", import.meta.url))` in the virtual module (build).
- **`ghia build` compiles by default**, through `Bun.build` (`compile: { outfile }`, `format: "esm"`, `naming: "[name].[ext]"`, `bytecode`, `minify`) with `dist/main.js` and, when there is one, `dist/server.js` as entrypoints. The Worker has to be an entrypoint, or the binary fails with `ModuleNotFound /$bunfs/root/server.js`. `autoloadBunfig: false` and `autoloadDotenv: false` are hardcoded: a shipped binary must not load a `bunfig.toml` (a test preload) or a `.env` from whatever directory it is launched in. A plugin deletes `const require = createRequire(import.meta.url)` from `@ghia/native/index.js` (matched by the pnpm path and by `packages/native/index.js`), because Bun's bundler embeds an addon only for a free `require("./x.node")`; it throws when the line is gone, since that means the napi-rs loader changed shape. `naming` is explicit because with Bun 1.4.4's default naming a compile of nine or more entrypoints (the app, the server and their Workers) loses its entrypoints under `/$bunfs/root/` and every Worker fails with `ModuleNotFound`; `[name].[ext]` keeps them at their file names. `ghia build --no-compile` and `build({ compile: false })` skip the compile. `Bun.build` is used because the CLI's `bun build --compile` takes no plugins. The binary is about 128 MB, 38 MB of it the addon.
- **App Workers are found the way web bundlers find them, at build time, with no config list.** `ghia()` returns two plugins; the second, `ghia:workers` (`workers.ts`, build only, both environments, inert under vitest), has a normal-order transform that runs after Vite's TS and JSX transforms, so the match is on plain JS. It matches `new Worker(new URL("<relative literal>", import.meta.url)` on the code with comments and string contents blanked (`strip-literal`, as Vite does), so a JSDoc example does not count, and rewrites the original. It is separate from the main plugin because the entry's `dom-globals` import is a `pre` transform and must not wait for that. The Worker file is **bundled as a build of its own**, like Vite's `bundleWorkerEntry`: a nested `createBuilder` of the same config file and environment (`builder.sharedConfigBuild`, which resolves the config once instead of once per environment: 40 config evaluations became 13 for an app with 9 Workers), with the Worker as the only input, `write: false` and `output.codeSplitting: false`. Its entry chunk becomes `this.emitFile({ type: "prebuilt-chunk", fileName: "<stem>-<hash8>.worker.js", code, isEntry: true })` of the outer build, together with the chunks of the nested build that are the Workers that Worker starts. It is a prebuilt chunk because Vite deletes every emitted asset (except `.js.map`) from the build of a `consumer: "server"` environment (`build.emitAssets` is false), and a prebuilt chunk is written verbatim without being bundled again. `isEntry` is what `ghia build` reads to list the compile entrypoints, with no name check. A Worker emitted as a chunk of the app build would share modules with `main.js`, and a shared module is split out and imported before the `@ghia/native/dom-globals` import of the entry. Each Worker is a build, so the config file and every plugin's build hooks run once more for it. The nested build is marked with an `inlineConfig` key (`ghiaWorkerBuild`); the main plugin then adds no `dom-globals` import, and the `server` environment bundles the Worker file instead of the virtual server main. A Worker whose URL is its own file is not built again: the URL is its own file name, and an A -> B -> A cycle is an error naming the chain. A failing nested build is rethrown with the Worker's path and its ANSI colors stripped, the cause attached. With `build.sourcemap`, the nested chunk's `sourceMappingURL` is pointed at the Worker's own file name and its map is emitted as a `.js.map` asset, because Rolldown does not write the `map` of a prebuilt chunk. Both Vite environments are `consumer: "server"`, so Vite's own `workerImportMetaUrlPlugin` (client only) never runs. The flat name sits next to `main.js` and `server.js`, which is where `/$bunfs/root/` has the Workers; every chunk is flat too (`chunkFileNames: "[name]-[hash].js"`), because a Worker URL is relative to the chunk that holds the call. `<hash8>` is the first 8 hex digits of a sha256 of `<environment>:<path relative to the Vite root>`: deterministic, so the `ghia` and `server` builds, which share an output directory, never write two Workers to one name, even for one file. `ghia build` takes its compile entrypoints from the output of each `builder.build(env)`, not from plugin state, because Vite resolves a fresh copy of the plugin for every environment build. Virtual modules (the built `virtual:ghia/server`) are skipped, and so is a Worker URL that does not resolve inside `node_modules` (a warning). In dev nothing is transformed: the module runner's `import.meta.url` is the real file and Bun loads the `.ts` Worker directly, resolving its imports itself.
- **The built `virtual:ghia/server` listens for the Worker's `error` event** and reports it, so a server that fails to start ends the app instead of leaving the UI waiting on a port nobody answers.

## React Fast Refresh

`react()` (`@ghia/react/vite`) is `@vitejs/plugin-react` for the JSX transform, plus the pieces that plugin only wires for a `client` consumer, which the `ghia` environment is not:

- **Vite's own transform leaves the refresh registrations out for a `server` consumer,** and plugin-react's wrapper (`vite/internal`'s `reactRefreshWrapperPlugin`, the native module that adds the `$RefreshReg$` prologue and the `import.meta.hot` boundary check) applies to `client` only. `react()` runs `transformWithOxc` with `jsx.refresh` on every `.tsx` and `.jsx` file of the `ghia` environment, and applies the same wrapper plugin to that environment, in dev only.
- **The refresh runtime reaches `globalThis` through a first import of the entry,** a virtual module that does what plugin-react's `index.html` preamble does: `injectIntoGlobalHook(globalThis)` and the default `$RefreshReg$` and `$RefreshSig$`. Everything depends on it running before `@ghia/react` evaluates, because the reconciler registers with the hook while it loads (`injectIntoDevTools` in `reconciler.ts`). It imports `@ghia/native/dom-globals` first, since the wrapper's code reads `window`. Without it the first component module throws `can't detect preamble`; `packages/react/src/__tests__/vite.test.ts` asserts that.
- **A full reload evaluates a fresh runtime,** because the runner's cache is cleared and the runtime is an ordinary module of the graph. The new run's reconciler registers with the hook through the new runtime's patched `inject`, so refresh works after any number of reloads (tested for one and two).
- **`react` and `react-reconciler` are external in dev.** They are CommonJS, and Vite's module runner cannot evaluate CommonJS (`module is not defined`), which `noExternal: true` would hit. Bun loads them natively, one copy for the app and `@ghia/react`. `ghia build` bundles them.
- **`react({ include, exclude })`** scopes the plugin to some files, because React and Solid both compile `.tsx` and one Vite config for both has to say which is which; `solid({ include, exclude })` is the same. `examples/vite.config.mts` gives Solid `examples/solid/**` and React the rest. The setup import goes only into an entry the plugin owns.
- **The server environment gets neither plugin's transforms.**

## Solid libraries compile from source

A Solid library is written for a renderer, and the DOM renderer is the one it was compiled for when it ships `dist/*.js`. The libraries that publish JSX under the `solid` export condition (Kobalte, Corvu's utilities) leave the choice of renderer to the app, so `solid()` compiles them with Ghia's like its own files: the environment has `noExternal: true` and vite-plugin-solid adds the `solid` condition and compiles every `.jsx` it is given.

Two things stand in the way, and `ghia:solid-libraries` (`solidLibrarySource()` in `packages/solid/src/vite/library-source.ts`, added to the plugins `solid()` returns) (the environments `solid()` already applies to, not the server Worker) removes them:

- **`@ghia/solid` from inside `node_modules`.** The compiled code imports it, and a library in a pnpm store (`node_modules/.pnpm/<lib>/node_modules/<lib>`) has no `@ghia/solid` beside it, and a package that is not `@ghia/solid` cannot self-reference it. A `resolveId` hook (`order: "pre"`) answers `@ghia/solid` and `@ghia/solid/*` from any importer with the file in the plugin's own package, taken from its `exports`. The plugin is loaded from the app's `@ghia/solid`, so the library and the app share one instance, which the contexts and the host tree need.
- **`solid-js/web`.** The same hook resolves it to `@ghia/solid/web` (`packages/solid/src/web.ts`): `export * from "solid-js"`, `Dynamic`, `createDynamic`, `Portal` with the structure of Solid's (an effect, a container appended to the mount, removed on cleanup), `isServer = false` and the universal helpers. Nothing the DOM compiler's output calls is there, and no shim stands in for it: the decision is that Solid's DOM renderer is never made to work on Ghia.

A library that ships only DOM-compiled output imports `template` and the like, and nothing can run it. A `transform` hook (`order: "pre"`, parsed as the file's own language, because Vite's import analysis rewrites the specifier later) fails any module whose code contains `solid-js/web` and imports or re-exports a name outside `WEB_EXPORTS` (`src/web-exports.ts`, kept equal to `web.ts` by `web.test.tsx`), naming the module, the names and the cause. The cost is a substring filter on every module and a parse of the few that match, at transform time only. The npm packages `@photon-ai/base-ui-solid` and `@msviderok/base-ui-solid` publish compiled output and no `solid` condition, so they fail this way.

Tests: `packages/solid/src/__tests__/vite.test.ts` (a library laid out as a pnpm store, under `ghia dev` and `ghia build`, and the failing compiled one) and `web.test.tsx`.

## A full reload is a page reload

A full reload under `ghia dev` unmounts the roots, keeps the window, and then runs the entry again (`createFullReload`'s `stop`, `unmountAllRoots` from `@ghia/native/roots`). Each adapter's root registers its unmount with `registerRoot` (`packages/native/js/roots.ts`, a set on `globalThis`, like the element sources), and the same unmount `render()` runs before it mounts again runs here, so the window, the renderer and the frame loop stay.

The reason is what the entry writes before `render()`: `document.documentElement.classList.add("dark")`, `document.body.addEventListener(...)`. With the old root still mounted those land on its `<html>` and `<body>`, which `render()` then destroys, and the new root starts empty. After the unmount `document` answers with fresh stand-ins, so the rerun entry writes to them and the first root's mount carries them over, as it does on the first run ([deviations](deviations.md#dom-building-from-code)): the page-reload semantics, where script that runs at the top of the page applies to the new page. A listener added to `body` is on the new `body` once.

- **A component edit never takes this path.** Solid HMR and React Fast Refresh updates do not fire `full-reload`, so they unmount nothing and keep the tree.
- **A throwing `stop` is logged and the reload goes on,** so an app whose teardown fails can still reload.
- **An entry that fails to evaluate leaves an empty window,** where the old tree used to stay until the next good save; the error is logged.
- **`bun --hot` has no such hook.** The entry runs again with the old root mounted, so its writes before `render()` still land on the outgoing `<html>` and `<body>`. `ghia dev` is the supported loop.

## Not decided


- Editing `vite.config` in `ghia dev`, and a UI full reload that re-runs the entry on the same `serverPort`, leaving the old run's listeners on it.

## Measured, and where

Both spikes ran on 2026-11-06 on one Mac, headless (the test renderer or plain Bun, never a live window), so no frame-time effect of the Worker is known. Each has a `FINDINGS.md` with the method:

- Renderer spike, `~/spaces/scratchs/ghia-renderer-spike/FINDINGS.md` (Bun 1.4.4, oRPC 1.16.2, TanStack Router 1.170 and Query 5.106): export conditions under Bun, the global `window`, and the transport comparison (median of five runs; a plain Bun process stood in for the UI, sequential calls only).
- Vite spike, `~/spaces/scratchs/ghia-vite-spike/FINDINGS.md` (Vite 8.3.6, vite-plugin-solid 2.11.15): the `ghia` environment, solid-refresh, the build, and the start and HMR timings above.

The behaviour is pinned by `packages/ghia/src/__tests__` (the CLI, spawning `ghia dev` and `ghia build`, with and without a server, and `dev()` and `build()` called in process), `packages/solid/src/__tests__/vite.test.ts` and `consumer.test.ts` (an app installed from tarballs with pnpm).
