# Editing hosts, ranges and the node selection

`contenteditable` is the DOM model of an editing surface: which elements are editable, which of them take focus, a live `Range` over the DOM, a `Selection` of nodes, and the Input Events an edit fires. It exists so an editor written for the web (Lexical is the target) runs unchanged. Phase 1 is the model and the event sequence; phase 2 paints the selection (the wash and the caret, below), and the pointer and the keys come after it, so a click does not place a caret ([deviations.md](deviations.md#events-and-input)). The API an app author sees is in [reference.md](../reference.md#editing-hosts).

## Editable elements and editing hosts

An element's own `contenteditable` is `true` (an empty text too), `false` or `plaintext-only`, ASCII case-insensitive, or it has none (no attribute, or a text that is no keyword) and takes its parent's. An editing host is an editable element whose parent is not editable. Two modules keep the same rule, one per side:

- `js/editing/host.ts` answers `isContentEditable`, `editingHostOf(node)` and `isEditingHost(element)`. `contentEditable` itself is reflected in `js/dom/reflected-members.ts`.
- `src/html/editing.rs` answers `own_value`, `is_editable` and `is_editing_host` from the props native holds (React writes `contentEditable`, Solid and `setAttribute` write `contenteditable`; `is_prop` names both).

**Focus.** An editing host is focusable, with `tabIndex` 0, and nothing inside it is: the editable descendants take no focus of their own. `RetainedTree::takes_focus` adds "is an editing host" (and has a box: a `display: contents` element is not one) to `needs_focus`, and `focusable_ids` holds the result. What decides it is the *parent's* editability, so it is not a function of the element's own props: it moves with a prop write on any ancestor and with a reparent.

- A `contenteditable` write retracks the element's subtree (`track_focusable_subtree` in `set_custom_prop`).
- A reparent retracks the moved subtree in `append_child`, `insert_before` and `detach_child` while `editable_count` is non-zero, the count of elements with their own `contenteditable` (as `inert_count` gates the same retrack for `inert`). React writes an element's props before it appends it, so `<div contentEditable><p contentEditable/></div>` registers the `<p>` as a host while it has no parent, and only the append makes it a descendant.
- Every element whose focusability flips in a retrack is `mark_render_changed`: nothing in its own props changed, so a retained root holding it would otherwise replay the tab stop and focus registration it had ([retention.md](retention.md)).

**Composition.** `src/editing/composition.rs` keeps the marked text on the tree (`RetainedTree::composition`) as two DOM positions, not as snapshot offsets: the snapshot is made again after every edit from wherever the selection is, and the positions are what survives that. `marked_text_range` turns them into offsets of the snapshot it was asked in, and answers `None`, forgetting the mark, when a position's text node is not in the snapshot, the selection is not inside the marked text (a caret at either edge is), or the mark is another host's. A focus change ends it too (`FocusState::push_change` calls `Composition::focus_left`). `replace_and_mark_text_in_range` sends `mark`; native then reads the new snapshot, where JS has put the selection as the platform asked (`new_selected_range`, relative to the new text, or its end), and the marked text is that many units before it. `replace_text_in_range` and `unmark_text` end it. The platform's replacement range is the one the event carries; with none, a running composition's marked text goes in as the range, so JS is never left to guess it, and `isComposing` on the event says whether a composition was running. In JS (`runEditingComposition`, `js/editing/input.ts`) the composition is a live `Range` per host: `mark` is `compositionstart` the first time, `beforeinput` (`insertCompositionText`, not cancelable), `compositionupdate`, the change, `input` (`isComposing`), and then the selection inside the new text; `insert` while composing is the same with the final text if it differs from the marked one, the caret after it, and `compositionend`; `unmark` is `compositionend` and keeps the text; a mark of no text is the input method cancelling: the text goes and `compositionend` has no data. A composition native dropped (the selection left it) is ended before the next edit starts another, and a host that loses focus fires `compositionend` before `blur` (`endCompositionOnBlur`). Chrome's `beforeinput` comes before `compositionupdate`, and the `input` of a commit still has `isComposing` true: the order phase 1 chose, kept. A key the input method takes is a `Process` `keydown` with `isComposing` set by `marked_text_range`, and a plain `keydown` that arrives while composing does not run the Enter and Backspace defaults. A dead key (Option+E, then E) is a one-character composition and runs through all of this. The marked text is read from the tree after the call returns, so it needs the edit to have run: a `mark` that was queued (no JS call on the stack) is not tracked reliably, and the composition is whatever JS makes of the queued events.

**Where things are.** `bounds_for_range` is the first rect of the range's text (`text_range_rects`) in window coordinates, which is what gpui positions the candidate window by, and the caret rect of the line for an empty range; an empty line has no text, so it is where the caret of the empty line was painted. A range that runs into another paragraph has the rect in the one it starts in. `character_index_for_point` is `caret_position_from_point` as an offset of the snapshot, and `None` when the paragraph under the point is not in it. The test renderer reads both without a platform (`getInputMethodBounds`, `getInputMethodIndexAtPoint`); they call the same functions.

**Keys.** A focused element that is editable (a host, or anything inside one) leaves the arrow keys, Page Up and Down, Home, End and Space to editing, as a focused `<input>` or `<textarea>` does: `GpuixView::scroll_by_key` does not scroll for it (`html::editing::is_editable`).

**`:read-write` and `:read-only`.** `:read-write` matches an editable element as well as the text controls, in `js/dom/selectors.ts` and in `src/css/sheet/tree_states.rs`; a `contenteditable` write refreshes the states below the element (`sheets_tree_state_changed_below`).

## Ranges

`js/dom/range.ts` has `AbstractRange`, `StaticRange` and `Range` with the standard's boundary-point algorithms (`js/dom/tree-order.ts` for the position of two nodes). `getBoundingClientRect` and `getClientRects` of a `Range` are interim: they give the start container's element rect.

A `Range` is live: a change to the tree moves its boundary points as the standard says. `js/dom/live-ranges.ts` holds the ranges weakly and implements the steps: `liveRangesBeforeRemove(parent, child, index)` before a child leaves, `liveRangesAfterInsert(parent, index, count)` after children arrive, `liveRangesReplaceData(node, offset, count, addedLength)` for a text change, and `liveRangesSplitText`. Each returns at once while no range exists (`hasLiveRanges()`), so a page that never makes one pays a counter check per tree change.

### The adapter contract

Children and text live in adapter mirrors, not in the node classes, so the node classes cannot see every change. **Every child or text mutation an adapter makes calls the hook exactly once, and a path that is reached through the DOM API must not call it again.** One missing call leaves a range pointing at a stale index; two move it twice.

| Change | Where the hook is called | Hook |
|---|---|---|
| A child is added (a framework commit, `appendChild`, `insertBefore`, a fragment) | React `linkChild` (`react/src/reconciler/host-nodes.ts`); Solid `insertHostNode` (`solid/src/host.ts`), after the splice | `liveRangesAfterInsert(parent, index, 1)` |
| A child is removed (including the removal half of a move) | React `unlinkChild`; Solid `removeFromParent`, before the splice, with the old index | `liveRangesBeforeRemove(parent, child, index)` |
| Text data through the DOM (`data`, `appendData`, `insertData`, `deleteData`, `replaceData`, `textContent`) | `replaceData` in `js/dom/nodes.ts`, once, before `binding.setData` | `liveRangesReplaceData(node, offset, removed, added)` |
| Text data the framework commits without the DOM API | React `commitTextUpdate` (`host-config.ts`); Solid's universal `replaceText` (`universal.ts`) | `liveRangesReplaceData(node, 0, oldLength, newLength)` |
| `Text.splitText` | `nodes.ts`, after the new node is inserted | `liveRangesSplitText` |

The DOM-path setters are the other half of the rule: React `setDomTextData` (`dom-mutation.ts`) and Solid `replaceHostText` (`host.ts`) are what `binding.setData` calls after `replaceData` has notified, so they must not notify. The framework paths bypass `replaceData` and so notify for themselves. A new adapter, or a new way an adapter changes a child or a string, keeps one call per change.

## The node selection

`js/dom/selection.ts` is the one `Selection` of the app, and it is one of two things: a live `Range` over the DOM (after `collapse`, `setBaseAndExtent`, `addRange`, `modify` or the caret of an editing host) or the painted-text selection a drag makes. They never exist together: selecting nodes clears the painted text and the drag drops the range. The range the selection owns is registered as a live range, and a boundary moved by a tree or data change makes it dispatch `selectionchange` (one per task, only while a listener exists). `Selection.modify` and the deletion keys read text through `js/dom/selection-movement.ts` and `text-segmentation.ts`: grapheme and word steps over the Text nodes around a point, a block edge or `<br>` as one step, a `contenteditable="false"` element as one atomic stop. It has no layout, so `line` and the other layout granularities throw.

**The caret goes in at focus.** A caret is placed at the start of an editing host, unless the selection is already inside it, whenever focus moves into the host:

- `element.focus()` does it in `focusHostElement` (`js/focus.ts`).
- Focus that native moved (Tab, Shift+Tab, a click) does it where JS first hears of it: `createRendererState`'s `dispatch` and `dispatchSync` call `placeCaretOnFocusIn` on a `focusin` before the event is delivered, so a listener sees the selection. A click behaves like Tab for now; phase 2 puts the caret at the point.

### Painting the node selection

JS sends the selection to native with `setNodeSelection`, the last op of a batch ([reference.md](../reference.md#wire-format)). `js/editing/node-selection.ts` writes it from `createMutationQueue`'s `flushMutations`: it compares the selection with what the root was last sent (`takeNodeSelectionWrite`), so one batch carries the state at flush time, an unchanged selection sends nothing, and a selection that moved to another root sends `null` to the one it left. The `Selection` tells the module on every change (`subscribeNodeSelection`: a new range, a boundary that a tree or data change moved, none), which asks the queues of the roots concerned for a flush (`requestMutationFlush`), so a change made outside a commit is painted by the next frame. Boundaries go as they are: a node id and an offset, UTF-16 code units for a Text and a child index for an element, and native resolves an element boundary to the text next to it.

Native keeps it on the tree (`RetainedTree::node_selection`, `src/editing/node_selection.rs`), not in the painted-text `SelectionState` whose identity makes a frame built whole. After a batch that set it, or that changed the shape of the tree or a text while a selection that is not collapsed exists (`refresh`), it works out which paragraphs the selection reaches: the Text nodes from the start boundary to the end one in tree order (a walk from the start, not a scan of the document), each located to its paragraph (`positions::locate`), and the two ends as Text positions (an element end takes all the text before it). A paragraph asks for its own bytes while it is built (`NodeSelection::wash_range`, in `paragraph_content`): from the start's byte if the start is in it, else 0, to the end's byte if the end is in it, else the end of the text. Those bytes are `SelectableText::node_wash`, painted in the same `wash_color` as the dragged selection, after it.

**The selection is a per-paragraph paint input.** The paragraph reads the selection when it is built, and a retained root replays what it built, so a change has to reach the root: `node_selection::update` marks each container whose paint differs with `mark_render_changed`, which is the paragraphs covered by one state and not the other, and the containers that hold a boundary only one of them has (an end that moves changes the paragraph it left and the one it came to, and not the ones between). A paragraph that is covered in both and holds no moved end is not marked, so moving a focus down a long selection builds two paragraphs. Nothing touches the frame identity, so a change to the selection does not make `all`: a frame skips every paragraph that was not marked (the tests count it).

**It is not a patch frame yet.** The mark is a layout change attributed to the container, and gpui's patch of the root that holds it is declined: the layout did not change, so it is a paint patch (`relaid` false), which writes the primitives over the ones recorded and needs the same operations (the wash adds and takes away quads: `Operations`) and, with retention skipping the unchanged paragraphs of the root, the same registrations (14 dispatch nodes against the 26 recorded: `Registrations`). The frame is then built whole, through retention, so what it costs is the paragraphs marked and the spine above them. Making it a patch needs a constant operation list (a quad for every row of a paragraph, transparent where nothing is washed, as `keeps_background_quad` does for a hover's background) and a root that is built whole, or a mark that dirties the layout so that the relayout patch (which rewrites the recording) takes it. That is an open design question. `RegEntry::node_wash` keeps the washed bytes with the registered text, so a replay puts back the wash with the text and the retention verifier compares it (`same_text_apart_from_transform`), and the paragraph digest includes it.

What is not covered: a restyle that moves paragraphs into or out of the covered set without a change of tree shape (`display` toggled on a block inside the selection) is not seen until the selection or the tree next changes. A collapsed selection is marked at its ends only: the paragraph that holds the caret is the one that paints it.

### Painting the caret

A collapsed selection in an editing host (JS sends the host's id with it, `setNodeSelection`'s last field) is a caret, and the paragraph that holds it paints it: a quad of `CARET_WIDTH` and the height of its row at `position_for_index(byte)`, in `SelectableText::caret`'s paint, after the wash and under the glyphs. Which paragraph and which byte is `NodeSelection::caret_byte`, asked by `paragraph_content` with the paragraph it builds: a boundary in a Text is `positions::byte_of`; one in an element is where the content next to it is (`element_boundary_byte`), the start of the child after the boundary (a Text, an atomic inline, an inline box, a `<br>`), else the end of the one before, else the empty inline box itself. So Lexical's empty `<p><br></p>`, which JS puts at `(p, 0)`, is byte 0 of the paragraph `"\n"`. A boundary next to a block, or in an element with no inline content (`<p></p>`), is in no paragraph and paints nothing ([deviations.md](deviations.md#events-and-input)).

It is shown while the selection is collapsed in a host that has focus (`focus_handles[host].is_focused`) and the window is key (`editing::caret::is_shown`), and painted in `theme.caret` (there is no `caret-color` in `StyleDesc`). The blink is the input's: `src/caret.rs` holds the constants, `caret_visible` and `until_phase_change`, and `input.rs` uses them. The state is the view's (`GpuixView::editing_caret`, `editing::caret::EditingCaret`): a clock that starts over whenever the selection changes (`NodeSelection::generation`) or the caret comes into view, and one task that waits for the end of the phase and asks the window for a tick (`Window::request_tick`), armed by the build of the paragraph while the caret is shown, so a host with no focus or a window that is not key asks for no frame. Painted in both phases (in no colour while it is off), so that the operations of the paragraph do not change with the phase.

**A blink is a tick that builds the paragraph alone.** The paragraph's container notes `Retain::blinks` whenever it holds a caret, shown or not, so it is a unit like the editor of an `<input>` ([patch-frames.md](patch-frames.md#an-editing-hosts-caret-is-a-tick)). `Sources::clock_due` asks `EditingCaret::due(id, shown)`: the phase changed since the paragraph was painted, or it painted the caret shown or hidden and it is the other now, which is how focus and the window going key reach a paragraph that no mark touched. Moving the caret is not a tick: the selection change marks the two paragraphs (above) and the frame is built whole through retention, as for the wash. A selection that moves alone marks with a barrier (`RetainedTree::mark_render_changed_unfollowed`), so a host that is a box root (a definite width and height) does not patch the move: the unit a patch of the paragraph it marked paints is not one the verifier's whole build records (`a patched frame differs from the frame built whole: the frame built whole did not record the root`, for a host with one paragraph), and the move is a frame built whole anyway everywhere else. A selection that moves in the batch of a text or tree change (typing) is marked as a change a box root's relayout follows, so the edit and the caret are one patch there. The first change of phase after the caret comes or moves is a frame built whole too: the paragraph was replayed, not built, in the frames since it noted the blink, and a unit is made by a build that finds the note.

`getPaintedNodeSelection().caret` reads what the last frame painted: `{ key, rect, lit }` in window coordinates, or nothing. `RegEntry::caret` keeps it with the registered text, so a replay puts it back and the retention verifier compares it (lit included).

## The editing input sequence

`js/editing/input.ts` runs one edit: `beforeinput` (an `InputEvent` that bubbles, is cancelable and composed, at the host, with `targetRanges`), the change to the DOM, `input`. The change goes through the DOM members (`insertData`, `deleteContents`, `insertNode`), so a `MutationObserver` records it, live ranges and the selection follow, and a framework editor sees what it would see in Chrome. A composition is `compositionstart`, `beforeinput`, `compositionupdate`, the change, `input`, `compositionend`. Phase 1 edits text only: a paragraph or line break fires `beforeinput` and changes nothing, and so does an edit that would join blocks or remove an element. The test renderer drives it without a key: `simulateEditingInput` and `simulateEditingComposition` (`js/testing.ts`).

Two things start an edit on a real keyboard:

- **Text is the platform's.** `js/events/keyboard-defaults.ts` does not turn a printable key into text. The focused host registers the window's input handler and what AppKit (or the test renderer's `dispatch_input`) types goes to it, as for an `<input>` ([Native text input](#native-text-input)).
- **Enter, Backspace and Delete are the `keydown` default** of an unprevented key on a focused host (`editInEditingHost`), which starts `runEditingInput` with `insertParagraph` or `insertLineBreak` (Shift), `deleteContentBackward` or `deleteContentForward`. They are not text for the platform either, so the sync result says `handled` and native stops the key (below).

### Native text input

`src/editing/input_handler.rs` is an `InputHandler` for one editing host. What it answers comes from `src/editing/snapshot.rs`: the `data` of the `#text` nodes of every paragraph from the one the node selection starts in to the one it ends in, joined by a line feed between paragraphs (a caret is one paragraph; a `<br>` and an atomic inline have no character in it), with the selection as UTF-16 offsets into it. It is made from the tree and the node selection on every query, so it is always what JS last flushed, and it maps offsets to DOM positions both ways through one segment for each `#text` node (a range start belongs to the text after the offset, a range end to the text before it). A caret at an element with no text next to it is an empty snapshot.

**Registration.** `Window::handle_input` registers during paint and only for a focused handle, and gpui keeps the last handler across frames that do not paint its element: the platform window holds it, a frame that replays the paint of the element copies it (`reuse_paint_with`; a retained root records the handlers its range held), and a patch that repaints a unit puts back the ones the unit had (`register_input_handler`). An `<input>` relies on the same. A host has no element of its own to paint from, so a focused host gets one more child, `input_handler::layer`: an absolutely placed canvas of no size, pushed last in `build_host_container` after the digest. It is built in the frames that build the host, which includes the frame after every change of the host's focus (the focus bits are part of what retention compares), and it adds nothing to layout. The handler holds the tree and the callback and no bounds or text, so there is nothing a replayed frame could leave stale. Costs: the host's retained root holds a handler, which gpui does not move to another place (`NonRelocatable::InputHandler`), so a host inside a row that a scroll relocates builds that row again where an unfocused one is replayed; and a host that gpui culls (a subtree scrolled well out of view) is not painted and so does not register.

**An edit is one synchronous call into JS.** `replace_text_in_range`, `replace_and_mark_text_in_range` and `unmark_text` send an internal `editinput` event aimed at the host (`sync_dispatch::emit_full`): `inputType` is the kind (`insert`, `mark`, `unmark`), `data` the text and `editRange` the replacement range, when the platform named one, already as DOM positions (`[startNode, startOffset, endNode, endOffset]`). It is not a DOM event and is not gated by listeners: `createRendererState` handles it ahead of `handlesEvent` (`js/editing/native-input.ts`). Outside a composition `insert` selects the range if there is one, runs `runEditingInput` (`insertText`, or `insertReplacementText` for a non-empty range) and flushes the mutations before it returns, so that the platform's next question (the selection, after every insert) reads the new tree. Where no JS call is on the stack the event is queued like any other and applied in order; a replacement range in it is as it was when the platform named it. A range the snapshot cannot map is reported as an error from the napi call that is on the stack.

**Keys.** A focused element that is editable always gets its `keydown` (`key_payload` in `events/keyboard.rs` sends it even with no listener on the path), because the edits above are its default. When that default ran, the sync result has `handled: true` (not the event's `defaultPrevented`, which is the page's verdict) and `install_key_down` stops propagation as it does for a prevented key: macOS then does not hand the key to the input context, and the test renderer's `dispatch_native_keystroke` does not call `dispatch_input`, so Enter makes no line feed and Backspace nothing else. On macOS a printable key is a `KeyDown` first and the text second (`insertText`), and a key with no character goes to the input context first and comes back as the one `KeyDown` through `doCommandBySelector`, so each key is one edit.
